# 内存预算才是真相，档位只是它的天花板

## Status

Accepted（2026-11-20）。取代 `MEM_LEVEL` 作为"默认值选择器"的用法（`build.rs` 的 `cfg(mem_low|mem_middle|mem_high)` 与 `src/platform/limits.rs` 的三张绝对值表）；保留 [ADR-0019](0019-config-is-derived-once-at-the-composition-root.md) 的"组合根派生一次"。相关：[ADR-0023](0023-directory-convergence-and-materialized-config.md)（`run/` 归 data 根）。

## Context

- 资源参数由编译期 `MEM_LEVEL` 三档常量决定，与机器无关：2 GB / 4 核的 ARM 盒子上允许 512 连接 × 1 MiB body，64 核 / 64 GB 的服务器上 `low` 只给 32 连接。
- 管理员手写 `svcd.conf` 时无从判断某个值对这台机器是否合理；越界值被**静默**夹到字面量上限，事后查不到"被改成了什么"。
- 背压触点各自有独立上限（连接、流、在途字节、每插件队列），没有总量约束，"这台机器最坏占多少内存"无法从配置推断；其中两处队列深度是硬编码常量。
- 三档表是**绝对值**，预算小的时候会被不变量压平：同样的收缩之后三个档位几乎一样，区分它们的信息就没了。
- 旧的 high 档（512 连接 × 8 MiB 完整 body = 4 GiB）本身就在 2 GiB 预算上超额承诺。

## Decision

1. **真相是一次启动探测 + 一个量化后的内存预算 `B`。** 探测是纯函数（注入 `Machine`），读可用内存、cgroup v2 的 `memory.max - memory.current`、CPU 核数、`install`/`temp` 卷的可用空间；探测失败逐项退化为缺失，全缺失时 `B` 等于编译期上限，进程照常启动。`auto` 只把**可用内存**打 25% 折扣；显式 `mem_budget_bytes` 写多少就是多少（见 2026-11-21 修订：只受编译期上限约束，下限与量化只作用于 `auto`）。
   - 不把探测值直接当真相：`MemAvailable` 受页缓存影响，噪声可达几十 MiB。`auto` 的 `B` 进入派生之前**向下量化**到固定台阶（64 / 128 / 256 / 512 MiB，1 / 2 / 4 GiB …），同一台机器重启两次得到同一套形状与并发（story 27/29）；显式值不量化。
- **2026-11-21 修订**：显式 `mem_budget_bytes` 不再被 64 MiB 下限抬升，也不做量化。理由是下限与台阶是为「探测噪声」设计的；把配置里的 50 MiB 悄悄改成 64 MiB 会让文档与实际派生不一致，也让「50 MB 设备」这类测试无法表达。显式值只受编译期上限约束，且仍要过不变量（装不下就收缩/拒绝启动）。
   - 磁盘可用空间只进 `svc config tune` 的建议与状态展示，不进入派生与不变量（磁盘不是内存）。
   - **探测的每一项都可以被配置取代**（`probe_available_memory` / `probe_cgroup_remaining` / `probe_cpus` / `probe_install_free_disk` / `probe_temp_free_disk`）：写了的项以配置为准，并且**不再读 OS**；`0` 表示"未知"，也不回落到探测。理由是同一份配置要能在另一台机器上复现（story 14），而容器的 `/proc` 未必说真话；逐项覆盖而不是整块跳过，是为了只钉住需要钉的那一项。

2. **`MEM_LEVEL` 从"默认值选择器"改成"预算硬上限"，只收紧不放宽。** 128 MiB / 512 MiB / 8 GiB 分别是 low / middle / high 的上限（`high` 于 2026-11-21 由 2 GiB 抬到 8 GiB，见修订三）。删除它会让"发给受限 SKU 的二进制在此机器上最多规划多少"重新变成不可验证的运行时事实；保留成上限后，这个承诺对任意注入 profile 都成立，也因此可以写一条不依赖机器的测试（story 9/10/19）。
   - 它不再作用于任何单个键：单个键的上界来自份额 × 预算，编译期上限只作用于 `B`。

3. **形状用份额，不用绝对值。** `workload: tiny | interactive | streaming` 决定预算**怎么花**（每连接占多少预算、单体占多少、流与在途占多少），不决定花多少。每键上界 = `min(绝对上限, 份额 × 量化后的 B 反解)`；形状基准 = 该形状在**参考预算**下的期望值（tiny@128 MiB、interactive@512 MiB、streaming@2 GiB）。旧三档表降级为校准锚点与回归观察，不再是运行时常量。
   - 不按单键设绝对上限：那会回到十几个互不相干的硬顶，仍然没有总量约束。份额让"这台机器最坏占多少"成为可计算量。
   - 绝对值表会被不变量压平，份额不会：收缩按同一比例作用在份额上，三个形状在任何预算下仍严格可区分。**唯一的例外**是"并发"与"单体"不可能同时随形状单调上升——`连接数 × 单体` 是乘积，在 2 GiB 上给 streaming 768 连接就不允许 8 MiB 的单体。本文的选择：**单体在 interactive 达到峰值、streaming 用更小的单体换更多长连接**；测试 `the_shapes_never_collapse_into_one_result` 固定这一点（2026-11-21 修订二把「并发严格单调上升」换成「按余量反推」，见下）。

   - **2026-11-21 修订（二）：连接数不再是一份份额，而是不变量剩下的余量。** 一槽的最坏成本是 `单体驻留 + 流缓冲 + 线程栈`（tiny 在 50 MiB 预算下是 29 KiB），旧份额 `16 MiB/3` 把它高估了约 150 倍：50 MiB 只派生出 9 条连接，10 个插件各 1 个并发都装不下，实测第 5 个插件就撞 503。现在未显式配置时按 `(预算 - 其余各项) / 每槽成本` 解出条数（`Limits::fitting_connections`，上限 4096），显式值优先、随后照旧被不变量收缩。于是「预算即真值」对并发也成立：50 MiB 能放数百条连接，而不是 9 条。
     - **2026-11-21 修订（三）：`high` 的上限从 2 GiB 抬到 8 GiB，并新增 `mem_budget_percent`。** `auto` 取可用内存的 25%，2 GiB 的上限在可用内存 ≥ 8 GiB 的机器上让 `auto` 饱和：预算不再跟着机器走，而这正是本 ADR 第 1 条要避免的失败模式。8 GiB 让 `auto` 在可用内存 ≤ 32 GiB 的机器上仍然是真的 25%；`low`/`middle` 与级别名不变，CI 的三档矩阵不变。百分比键（1..100）把显式尺寸写成「可用内存的份额」，解析成字节之后与显式数字同路：只受上限约束、不做量化、仍过不变量；与 `mem_budget_bytes` 互斥，两者同时出现是配置错误。被上限夹住时报告里记一行 `mem_budget_percent: 90 -> <上限>`（左是配置值、右是生效预算的字节数），不静默改写。
   - 形状的顺序随之反过来：**单体越小，同样预算放下的连接越多**，tiny 最多、interactive 单体最大；`the_shapes_never_collapse_into_one_result` 改为断言这个方向，`the_reference_values_stay_close_to_the_historical_table` 不再为连接数设锚点（它已经是派生量，不是常量）。
     - `max_connections_per_ip` 未显式配置时等于连接数：控制台、CLI 和反向代理都从同一个地址来，低于全局上限的每 IP 上限会让全局上限永远用不满。
     - 代价：50 MiB 的 daemon 现在可能接受数百条连接。CPU 不再是隐形的——`cpu_budget_percent` 提供内核硬限与准入闸门，让「接多少」与「吃多少 CPU」分别可限。

4. **最坏内存是可读的不变量，超了就收缩，收缩不了就拒绝启动。**
   `worst_case = 常驻基线 + 线程数 × 线程栈 + 连接数 × (单体驻留 + 流缓冲) + 流数 × 流缓冲 + 在途字节 + 队列深度 × 帧上限`，按各项可同时发生的最坏叠加。`worst_case ≤ B` 不满足时按固定顺序：先按所需额度解出更小的单体驻留（不是直接压到地板，否则默认值一碰不变量就塌成最小可用 body），再降并发（下限 8），仍不满足则拒绝启动并在错误里列出各项与所需/可用预算。Windows 上每条被接纳的连接都占一条线程，所以线程项 = 两条循环 + 阻塞池 + `max_connections`（连接部分已经由 `max_connections` 封顶，`min(派生线程数, max_connections)` 说的就是这一点）。（2026-11-22 修订：Windows 改跑同一个 poll loop，连接不再是线程，线程项两端都是「两条循环 + 阻塞池」；见 [ADR-0027](0027-windows-runs-the-same-poll-loop.md)。）

   - **2026-11-21 修订（四）：基线换成实测值，连接槽加实测下限。** 常驻基线原本是 32 MiB 的设计猜测（`specs.rs` 的注释就写着「a measured baseline replaces it in #107」）；参考机上空载、无插件的 daemon 实测只有 3.4 MiB，32 MiB 在 50 MiB 预算里独占 64%，把名额压在 288。现基线为 **8 MiB**（实测的两倍余量）。同时连接槽原来只按「单体驻留 + 流缓冲」记账（tiny@50 MiB 是 29 KiB），而实测每条连接连同它那条插件监督项是 **75–77 KiB**，账面比物理低一半——「账面放得下」不再等于「物理放得下」。现每槽成本取 `max(单体驻留 + 流缓冲, 80 KiB)`。两条一起生效后：名额 50 MiB 288 → **405**、512 MiB 399 → **421**、2 GiB 786 → **797**；40 个插件、每插件 P 个五面客户端的 100% 成功点从 P=8（320 个客户端）抬到 **P=12（480）**，实测 daemon RSS 34.3 MB / 50 MB。代价说清楚：现在每槽按物理成本记账，所以「名额 × 每槽」更接近真实占用，账面余量从两倍收到约 1.4 倍。

5. **覆盖说明是派生结果的一部分，不是事后再算的日志。** 结构固定 `{ 键, 配置值, 生效值, 原因 }`，原因是枚举：高于上界 / 低于下限 / 不变量收缩 / 被编译期上限夹住。随配置一起派生、不可变；启动在日志初始化完成后逐条输出，daemon 同时把整个派生报告写到 `<data>/run/resources/startup.json`（独立子目录：`run/` 下的 `*.json` 是服务运行时记录），`svc status --resources` 读回上一次启动的清单。不新增管理 API、不引入热更新。
   - 高于上界回落到**形状基准**而不是上界：管理员的手滑应该回到一个正常值，而不是回到"恰好还能塞进去的最大值"。

6. **测试接缝不探测本机。** `Config::with_paths` / `Config::with_resources` 取注入的 `ResourceProfile`（缺省为空 profile，`B` 即编译期上限），只有 `Config::bootstrap` 读真实机器。同一份 `(配置, profile)` 必得同一份派生结果（story 14/17）。

## Considered options

- **删掉 `MEM_LEVEL`，完全信任探测**：受限 SKU 的二进制不再有可验证上限；无 `/proc` 的容器里 `B` 会掉到地板或上限，两者都不可控。否决。
- **保留三档绝对值表，只把档位改名为形状**：预算小时表会被不变量压平，正是本决定的起因。否决。
- **探测值直接进派生，不量化**：重启前后形状会跳变（story 27/29）。否决。
- **按单键设上限**：回到互不相干的硬顶，没有总量约束。否决。
- **不变量只在文档里，不校验**：`svcd.conf` 里巨大的 body 与海量连接仍能把进程拖到 OOM 才死（story 25）。否决。

## Consequences

- 一台新机器首次启动就得到合适的并发与缓冲；管理员不再需要读构建脚本。
- 显式调优值要么生效、要么带原因被改写；"没生效"不再需要猜。
- 三处背压队列深度进了配置与派生表（`pending_queue`、`progress_queue`，以及 `ws_raw_queue` 的默认值），"最坏内存"覆盖全部 admission 点。
- 旧 `svcd.conf` 不加新键照常启动：缺省值全部来自派生。
- `svc status --resources` 显示的是**上一次启动**的快照；daemon 从未在这台机器上启动过时它退化成"本进程的派生"，并明确标注来源。
- 三档历史数值作为校准锚点保留，`docs/testing.md` §4 的形状矩阵改为按 `workload` 三值 + 预算台阶跑。
- 不在本决定内：按负载反馈调参、按插件分配配额、磁盘空间驱动的清理、免重启热更新、吞吐基线工具本身（#107）。
