# S4 请求交接：服务器持有连接，对外面只解释请求

## Status

Accepted。细化 [ADR-0012](0012-protocol-is-server-plus-face.md)；切片见 #113，server-loop 已由 #114 接管 HTTP listener / 连接，#115 落地 sans-IO stream handler 并让插件 UI 静态资源穿过它，#116 接线阻塞池与首个 `Blocking` 路由，#117 把剩余管理 JSON、login/logout 与控制台页移入 face，#118 让 blob/file 下载穿过 stream handler，#119 让 blob/file 上传穿过同一接口，#120 让 export spk/spkb 穿过同一接口，#121 让 import/install 上传穿过同一接口，#122 让插件 UI 的 SSE / WebSocket / raw WebSocket 改走 stream handler，#123 让 MCP SSE 进度流穿过同一接口，#124 把控制通道与出站管理流并入 server-loop，#125 删除 legacy bridge / HTTP worker / takeover / temp-cleaner，后续迁移见 #126。

## Decision

- **连接只有一个所有者：服务器。** 服务器持有 fd、读缓冲、写缓冲、deadline、pending 表、keep-alive 与背压；对外面拿不到 socket、文件描述符、连接 guard，也拿不到连接上的超时。
- **Unix 的 server-loop 在 `server/http/engine.rs`，连接状态机在 `server/http/server.rs`。** 它拥有 HTTP listener（可缺省）、控制通道 listener、出站管理流 socket、连接表、请求缓冲、pending 请求与写回。没有 legacy bridge、没有独立的 HTTP worker 队列：face 之外的剩余路由（MCP、插件 UI rpc、blob/file 会话元数据）作为 blocking job 提交给共享阻塞池，池队列上限 64，满时 503（带 `Retry-After: 1`）。close/超时仍由 loop 统一移除连接。
- **阻塞池是 server 的固定资源（#116）。** 默认 2 条 worker，`blocking_threads` 可配且 clamp 2..8；队列上限 64，队列满或同一连接已有排队/运行中的任务时返回 503 `busy` + `Retry-After: 1`，不增长队列、不起临时线程。池在 server-loop 装配时启动（早于 loop 线程），启动失败会让 HTTP 启动失败，而不是静默停掉所有路由。每个被接受的任务只回报一次结局：`Finished`（运行完成，槽里可能有结果）、`Cancelled`（运行中连接断开，结果丢弃）、`Dropped`（排队任务被取消或池关闭，从未运行）；server loop 按结局取槽或回 503。`Processing` 连接每个 tick 用 `MSG_PEEK` 检查对端 FIN（不消费下一请求的字节），断开时封住完成槽、翻转运行任务的 cancellation token，排队任务立即丢弃。Unix 的 `/api/v1/services` 是第一个 `Blocking` 路由；Windows 的每连接线程回退在该连接线程上执行 `Blocking` 路由，不引入共享池。
- **S4 是 server ↔ face 的请求交接 seam**，形状是「路由决策 + 一次完成式回调」：
  - `Face::route(method, path) -> Option<Route>` 回答「这条请求归不归我、请求体怎么处理」。契约要求它在读取请求体之前被调用；#114 接管连接后仍在收完 body 后才问 face（`Blocking` 路由已接线，route 提前到读 body 之前仍待后续切片）；
  - `Route { body, dispatch, public }` 是契约携带的路由/请求体决策。`body` 是 `Empty` / `Buffered { limit }` / `Streamed`；`dispatch` 是 `Inline` 或 `Blocking`；`public` 为 true 时服务器跳过 transport auth（login / logout / 控制台页），由 face 自己执行密码校验、cookie 清理与 console 投影。
  - `Face::handle(Request, Completion)` 只解释请求。`Request` 带 method、path、headers、peer、服务器解析好的 principal，以及按 body 策略给出的完整 body 或空 body。
- **交换只有两种结果**：`Exchange::Response(Response)`（status、content-type、headers、完整 body）或 `Exchange::Stream(Box<dyn StreamHandler>)`。`StreamHandler` 是 sans-IO 状态机：只收事件、返回动作，不读不写 socket。事件面是 `Data` / `Writable` / `Tick` / `BlockingDone` / `Closed`，动作面是 `Continue` / `NeedRead` / `NeedWrite` / `SubmitBlocking` / `SendFile` / `Close`；输出只能写进受限的 `OutBuffer`。`SubmitBlocking` 已由 #119/#121/#122 接线：server loop 把 job 交给 `BlockingPool`，job 的返回值经 `StreamJobDone` 回到同一个 handler，池的 `BlockingDone` 只负责释放唯一 key。
- **完成恰好一次。** `Completion::complete` 第一次被接受；第二次被拒绝、忽略并记日志。`Dispatch::Inline` 的 handler 必须在 `handle` 返回前完成；返回时没有结果，服务器记 500（`internal`），封住完成槽，之后迟到的完成也被忽略。`Blocking` 路由由阻塞池执行，完成回到 server loop 写回；等待 deadline 的通用机制仍待后续切片（`svc.list` 的 job 自身没有额外 deadline）。
- **结果必须与 route 的 body 策略一致。** `Streamed` 路由返回内存响应、或 `Buffered` / `Empty` 路由返回 stream handler，都是实现错误：服务器在发出响应头之前转成 500。
- **鉴权在服务器完成一次**：服务器把解析后的 principal 放进 `Request`；对外面只做端点策略（MCP bearer-only、插件 token、CSRF 等）。#113 的 `/api/v1/version` 没有额外端点策略。#114 仍沿用旧的每请求 `Lan::authenticate`；把 principal 提前到连接建立是后续 server-loop 工作。#117 的 public route（login / logout / 控制台页）在 `Route.public` 上声明，服务器跳过 transport auth，face 自己执行密码校验、cookie 清理与 console 投影。
- **#113 只让 `/api/v1/version` 穿过对外面**；#114 让 server-loop 接管全部 HTTP 连接；#115 让插件 UI 静态资源走 `Streamed` 路由；#116 让 `/api/v1/services` 走 `Blocking` 并新增固定 2 条阻塞线程；#117 把剩余管理 JSON、login/logout 和嵌入式控制台移到 `ApiFace`，管理面不再经过 legacy worker 队列。blob/file 下载（#118）、上传（#119）、export spk/spkb（#120）与 import/install（#121）已经走 stream handler。没有新增每请求或每流线程；#125 删除 4 条 legacy worker 与 temp-cleaner 后，Unix 默认 5 条（supervisor、server loop、插件 reactor、2 条阻塞线程），#126 合并插件 reactor 后 4 条；Windows 仍保留每连接线程回退。
- **管理面共用阻塞池的背压（#117）。** 除 `/api/v1/version` 和控制台页外，管理路由（含 `compat`、404/405 分支）都是 `Blocking`，与 `svc.*` 共用默认 2 条 worker；两个慢 RPC 会让后续管理请求按同一 503 + `Retry-After: 1` 失败，这是有意的可见背压，不新增线程。`/mcp`、插件 UI rpc 和传输 takeover 仍走 legacy 路径，直到 #118–#123。
- **请求体策略仍是「带着」而不是「提前用」**：server-loop 在 `pre_request` 里先给插件 UI、blob 上传和包上传检查原始 head，其余请求仍按旧上限收完 body 再交给 face。导出自从 #120 起是 face 的 `Streamed` 路由，不再需要这个窗口。把其余 face 的 route 决策移到读 body 之前仍待后续切片。
- **#115 的第一个 `Streamed` 路由是插件 UI 静态资源**：`PluginUiFace` 在 `pre_request` 里认领 `GET /plugin-ui/{id}/{token}/...`（`rpc` / `events` / `ws` / `raw` 仍走自己的路径），server 解析一次 principal 后把请求交给 face；face 返回 `PluginUiStream`，`server/http/driver.rs` 持有输出缓冲、transfer deadline、`max_streams` 槽与文件发送。HTML 只用 4 KiB 前缀定位 doctype，其余部分与其它资源一样通过 `SendFile` 走内核 `sendfile`（Linux）或 `TransmitFile`（Windows 线程回退的阻塞驱动），所以 server-loop 不读整页、一次页面加载也不为每个资源起线。鉴权失败仍由 server 呈现：浏览器导航得到 303 登录跳转，API 客户端得到 401。
- **一次性静态资源不占 `max_streams`**：handler 用 `StreamClass::OneShot` 声明这一点；长连接/传输 handler 默认 `LongLived`。`server/http/budget.rs` 的 `StreamBudget` 在 attach 时为 `LongLived` 占一个 `max_streams` 槽（满时 503 + `Retry-After: 1`），`OneShot` 完全不进计数；#118/#119/#120/#121 起由 stream driver 驱动的下载、上传、导出、包上传与 MCP SSE 复用同一预算；静态资源保持豁免。
- **#115 的 Windows 回退仍是每连接一线程**：`server/http/fallback.rs` 在连接线程上驱动同一个 handler，socket 与超时都在 server 层；页面加载不会额外产生 per-asset 线程，但也不承诺 Unix 的四线程目标。
- **#118 的 blob/file 下载是 sans-IO handler**：`face/blob.rs` 的 `DownloadStream` 保留旧的 Range、ETag、`If-*`、`If-Range`、HEAD 与 404/412/416 线路字节；单文件下载把 body 交给 server 做一次 `SendFile`，逻辑文件（多分片）按分片顺序多次 `SendFile`。为此 `SendFile` 不再是终态：server 发完一个 range 后再次投递 `Writable`，handler 可以请求下一段或 `Close`。下载以 `StreamClass::LongLived` 占 `max_streams`；预算移到 `server/http/budget.rs`，Unix driver 与 Windows fallback 共用；blob 上传从 #119 起也占同一预算。Unix 不再为下载克隆 socket 或起 `svcd-blob-http` 线程；Windows 回退在同一连接线程上驱动 handler。
- **#119 的 blob/file 上传是 sans-IO handler**：`face/blob_upload.rs` 的 `BlobUploadStream` 接手 `POST /api/v1/blobs` 与 `PUT /api/v1/{blob,file}/uploads/{id}/parts/{n}`（含 `/files` 别名），保留 simple、chunked、multipart、可恢复分片与 `Expect: 100-continue` 的线路字节。请求体由 server 作为 `Data` 事件投递；handler 只把一块交给 `SubmitBlocking`，driver 在排队/运行期间不再读 socket（背压），队列满时 blocking pool 拒绝该 job，server 把 `BlockingOutcome::Failed("the blocking queue is full")` 交回 handler，handler 立即写 503 `busy` + `Retry-After: 1` 并关闭；driver 同时暂停读取，并用 transfer timeout 给排队/运行中的暂停封顶，避免永久占槽。staging 的 `Upload`/`PartWriter` 在 blocking job 里创建、写入和 finish；断开或未完成的 handler 被丢弃时，Drop 删除临时文件。上传与下载共用 `StreamBudget`（`LongLived`），满时 503 + `Retry-After: 1`；Unix 不再起 `svcd-blob-http` 线程，Windows fallback 在同一连接线程里读 body 并内联执行 blocking job。
- **#120 的 export spk/spkb 是 sans-IO handler**：归档布局留在 `package::TarPlan`（.spk 的条目顺序、tar 头、padding、trailer）与 `plugin::plan_export_spkb`（backup.json + 嵌套 .spk + 活动 config），`face/export.rs` 的 `ExportStream` 只把计划投影成响应：小字节段写进受 `stream_buffer` 限制的输出缓冲，payload 文件交给 server 的 `SendFile`，所以大包不占内存、慢客户端只停自己的连接。产出与旧 takeover 逐字节相同（`backup.json` + 嵌套 `plugin.spk` + `config` + 1024 字节 trailer；`manifest.json` + `signature.json` + 按路径排序的 payload），HTTP 头（`Content-Type` / `Content-Length` / `Content-Disposition` / `Cache-Control: no-store`）也不变；CLI 导出的 `TarPlan::write_verified` 仍逐文件校验 `sha256`，与流式导出共用同一份布局。plan 在第一个 `Writable` 事件、也就是拿到 `max_streams` 槽之后才构建，满槽的 503 不付构建成本；导出以 `StreamClass::LongLived` 占共享 `max_streams`（满时 503 + `Retry-After: 1`），客户端断开时 driver 丢弃 handler，计划与文件句柄随之释放。路由在 `ApiFace` 里是 `Inline` + `Streamed`，Unix 不再克隆 socket 或起 `svcd-export-http` 线程，Windows 回退在同一连接线程上驱动同一个 handler。
- **#120 改写了“插件存在”的判断**：旧 takeover 在写响应前调用 `api::require_plugin`（`svc.status` 的控制通道往返，会阻塞 server loop），现在 face 只用 `package::valid_name` + `plugin::current_version` 的纯文件系统判断。结果是 core 服务 id 仍回 404，但消息从 `not a plugin: X` 变成 `unknown plugin: X`；一个在磁盘上存在、但不在注册表里的 plugin 目录会导出成功，而不是 404。导出因此不再依赖控制通道。
- **#120 的已知取舍**：流式导出的 payload 字节在内核里从磁盘到 socket，handler 看不到它们，所以不再逐文件复算 `sha256`；plan 仍在发出响应头之前拒绝缺失/截断的 payload（`installed file is corrupt`），导入路径会再次校验 `files[].sha256`。plan 构建在 server loop 上做 manifest/signature/config 读取与每文件一次 `stat`，其规模随插件文件数增长，与 #118 的下载路径同级（旧 takeover 在独立线程上做同样的工作）。
- **#121 的 import/install 是 sans-IO handler**：`face/install.rs` 在 `pre_request` 里认领 `POST /api/v1/plugins` 与 `POST /api/v1/import`，请求体按 `Data` 事件到达，每块交给 `SubmitBlocking`，由阻塞池喂给 `package::StagingInstaller`。这个增量安装器与旧路径共用同一套校验：manifest 先解析，签名在任何 payload 字节之前检查，tar 条目逐条对照 `files[]` 的 size/mode/sha256，最后 `validate_staged_payload`；区别只是字节由谁提供，tar 头和条目边界由 sans-IO `TarFeed` 在任意切分处保留。import 先攒到 512 字节再按第一个 tar 头分流：`.spk` 走同一个安装器，`.spkb` 的 `backup.json` / 嵌套 `plugin.spk` / `config` 由外层 `TarFeed` 逐条流式解析，裸 config 仍受 `max_body_bytes` 限制并走 `transfer::import`。staging 在 manifest+签名校验之后才创建，payload 边到边写、边算 sha256；客户端断开、包被拒绝或 daemon 拒绝 staged 安装时，Drop 删除 staging。`Expect: 100-continue`、`Content-Length > max_package_bytes` 的 413 与端点状态码保持不变；错误的 Content-Type/strategy 仍先回答再排空请求体，避免 Windows 的 RST 吞掉响应；该拒绝 handler 是 `StreamClass::OneShot`，不占 `max_streams`，所以满预算时仍是 400 而不是 503。包上传是 `StreamClass::LongLived`，与下载/导出共享 `max_streams`（满时 503 + `Retry-After: 1`）。阻塞池 worker 从 #121 起使用 `transfer_stack()`（至少 256 KiB），因为 job 现在会解析 tar 与 manifest；在 `request_stack_bytes` 的下限配置上，64 KiB 的池线程栈会溢出。Unix 不再有 `svcd-import-http` / `svcd-install-http` takeover 线程；Windows 回退在每连接线程上驱动同一个 handler。
- **#123 的 MCP `tools/call` 进度流是 sans-IO handler**：`server/mcp/progress.rs` 的 `McpSseStream` 保留旧的 SSE 头、chunk 编码、progress→final 顺序与 `-32603` 通道错误映射；`POST /mcp` 的 header 校验、bearer-only 鉴权与状态映射仍由 `mcp_http` 完成，server loop 只把管理流客户端的 64 槽进度队列交给 handler。open 之前先占一个 `max_streams` 槽：预算满时返回 503 + `Retry-After: 1`，不启动插件调用；客户端断开或 driver 丢弃时取消 outbound 调用并释放槽。旧的 `ConnState::McpSse`、`MCP_STREAMS` 计数与 429 `too_many_streams` 已删除；预算满时按 #112 的 busy 契约返回 503 + `Retry-After: 1`。Windows 仍走既有的每连接阻塞 `serve_mcp_sse`（#112 的回退豁免），但同样在写头前占、在函数结束时释放同一个 `max_streams` 预算；把 Windows 的控制/MCP 也并入同一 poll 仍属后续切片；当前保留 #112 的每连接线程回退。
- **#124 的控制通道与出站管理流**：控制 listener、每个 CLI 连接和 MCP 的 outbound streaming socket 都进入 server-loop 的同一个 poll 集（`server/control/`）。CLI 请求仍通过有界 `PendingCall` 通道（256 槽，满时该连接收到 -32000 并关闭）交给 supervisor-loop，回包经 `Reply` 与共享 wake pipe 回到 server-loop，由它写给发起连接；supervisor 从不碰客户端 socket。MCP 进度 socket 的读取也由 server-loop 完成，64 槽 handler 队列满时停止读上游（背压）。daemon 的 supervisor loop 退出后调用 `Api::shutdown`：server-loop 停止 accept、排空 control 回包并以短超时阻塞写完，然后 join，因此 `svcd.shutdown` 的回包不会随进程退出丢失。无 HTTP 的构建用同一个 engine 以 `None` listener 只跑控制通道。旧的 `channel_reactor` / `channel_client_reactor` 两条线程已删除，默认空载 12→10 条。Windows 仍保留每连接线程的 control fallback（#112），本切片的 poll 合并与 shutdown join 只在 Unix。
- **#122 的插件 UI 实时流**：SSE、页面 WebSocket、协议 3 raw WebSocket 都在 `face/plugin_streams/`。SSE 自己写 `Transfer-Encoding: chunked` 头、replay reset、15 s heartbeat 和带 id 的事件，输出受 `OutBuffer` 限制；页面 WebSocket 自己解析帧（`server/http/wire.rs`），`tools/call` 通过 `SubmitBlocking` 交给阻塞池，响应 id 在 job 内改写，通知从 UI bus 读；raw WebSocket 只收 binary 帧，分片先拼装，转发到 raw hub 的 `RawSubscription`，心跳与 1000/1002/1003/1009/1013 关闭原因沿用原状态机。三条流默认 `StreamClass::LongLived`，在 attach 时占 `max_streams` 槽；慢客户端由输出缓冲与有界 bus/raw 队列提供背压，不阻塞其它连接。两个引擎驱动同一组 handler：Unix 走 `StreamDriver`，Windows 回退在连接线程上做全双工读/写/`Tick`，阻塞 job 直接在该线程执行（该线程本来就只服务这一条连接）。

- **#125 删除 legacy bridge / HTTP worker / temp-cleaner**：`api/legacy.rs` 的连接状态机移入 `server/http/server.rs`，四个 `svcd-http-worker` 与有界 64 的 bridge 队列删除；face 之外的剩余路由（MCP、插件 UI rpc、blob/file 会话元数据）由组合层注入的 fallback handler 在共享阻塞池上执行，回包经 server loop 写回，不再有 per-request 线程。临时文件清理从独立 `svcd-temp-cleanup` 线程移到 supervisor loop 的定时器（`temp_cleanup_interval_secs = 0` 仍关闭）。Unix 默认空载 5 条：supervisor、server loop、插件 stdio reactor、2 条阻塞 worker；#126 合并插件 reactor 后 4 条。`engine::run` 仍由 full server 与 control-only 两个永久实现共享，但 trait 已从 "legacy bridge" 改名为 `ServerLoop`，不再有临时 endpoint 状态机或 worker 队列。

## Consequences

- face 的测试不再需要 socket：内存 `Request` + `CompletionSlot` 就能断言响应、恰好一次、缺失完成和二次完成。
- 服务器可以替换（Unix poll reactor、Windows 线程回退、将来的 IOCP），face 与端点测试不变。
- `StreamHandler` 出现后，ADR-0012 原来说的「交出连接」只表示「交出一个 sans-IO 状态机」，不再表示连接所有权转移；连接始终归服务器。
- #125 删除了 legacy bridge 与它的 HTTP 队列。阻塞池队列仍是有界 64，满时 503；池关闭时排队任务以 `Dropped` 回报（server loop 若还在运行会回 503），运行中的任务让它跑完并把结果写入已封的槽后丢弃。插件 UI 的 WS 任务已随 #122 从 legacy worker 队列删除；页面 WebSocket 的 in-flight 限额改为 handler 内的 `ws_inflight_requests` / `ws_inflight_bytes`，阻塞 job 走池。插件 UI takeover 已在 #115 删除；blob 下载与上传 takeover 已在 #118/#119 删除；export takeover 已在 #120 删除；import/install 两个 takeover 已在 #121 删除，包上传与下载/导出共用同一个 stream driver、预算与阻塞池。临时文件清理不再有自己的线程：supervisor loop 按 `temp_cleanup_interval_secs` 调 `blob::cleanup`。
- 本 spec 的最终线程目标（#126 合并插件 stdio 反应器后：「两条循环 + 两条阻塞线程，默认 4 条」）是 Unix 的默认拓扑。迁移期：#116 后 12 条，#124 去掉两条 reactor 后 10 条，#125 删除 legacy 后 5 条，#126 合并插件 reactor 后 4 条。Windows 本轮保留每连接一条线程的回退：它执行 `max_connections` / `max_connections_per_ip` / `http_idle_timeout_secs`，线程上限由 `max_connections` 约束，但不承诺 4 条线程；IOCP 留给 S3/S6。
- 完成槽封住后迟到的完成只能记日志，不能写回一个已经结束的请求；这消除 use-after-response 的竞态。
- `Blocking` 任务在派发前检查 cancellation token；`svc.list` 的 control-channel 往返本身没有可中断 deadline，连接断开后结果会被丢弃，但一个卡死的 daemon 仍会占住一个 worker。给 job 加自身 deadline 留在后续切片；阻塞池的队列上限保证不会因此无限增长。
- #117 的 face 仍复用 `api.rs` 的 control-channel / 错误映射 / `require_plugin` helper（S5 失败投影切片再搬）；`api → face → api` 的临时环仍在，但管理路由已不再进入 legacy worker 队列。
