# 复合服务：v1 边界

## Decision

- **v1 的复合服务只由 root 在 `services.d` 里定义**，复用现有加载、依赖、`enabled` 与重启策略。`.spk` 发布复合**延后**。
- **包发布复合若要落地，必须带显式能力授予清单**（这个包被允许调用哪些服务、哪些能力）。在补上这条之前，不允许任何包定义复合。
- **一条流暴露 0 或 1 个能力**：0 表示只被触发器启动的后台编排，1 表示同步入口。不允许多入口。
- **复合的能力面显式映射到流入口**，不从被调服务推导——推导会让上游插件加一个能力时，复合的能力面自动变大，构成意外暴露。
- **流在加载时静态校验**：引用的服务与能力存在、步骤图无环、能力面映射指向真实步骤。不通过就拒绝该定义并记一条 `LoadIssue`。
- **v1 的复合只在单机执行**；跨节点复合延后到 `cluster` 成熟，不在 v1 假装支持。

## Consequences

- v1 不需要能力授予机制，因为定义者就是 root；但这条边界必须在「包发布复合」之前补上，否则是权限升级漏洞（今天插件之间零互调）。
- 一条流一个入口，让输入映射保持一条线；多入口留给 v2，那时的代价是映射从一条线变成一张表。
- 「0 入口」是触发器流的必需品，不是特例——否则定时编排无法表达。
- 加载期校验把错误提前到 `svc reload`，代价是定义文件不能引用尚未安装的服务；部署顺序因此变成显式依赖。
- 单机执行意味着 v1 的复合不受网络分区影响；跨节点复合才会引入「节点不可达 vs 服务不可用」这对新失败类别，现在不需要决定。
