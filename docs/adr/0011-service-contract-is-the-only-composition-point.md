# 服务契约是唯一组合点

## Decision

- **一个服务只由「服务契约」定义**：能力面、调用信封、生命周期义务、健康语义、失败类别。契约之外没有第二种描述服务的方式。
- **运行方式只实现契约，不定义新接口**：本机进程、内置（core）、复合（一条流）、远程节点，四种实现归同一个类型。哪种实现由注册表条目指定，调用方不区分。
- **管理只生产契约实例**：从 `.spk` 或 `services.d` 得到服务，不定义运行方式；运行方式不属于包格式的一部分。
- **编排只能调用契约，禁止直接调用监督槽或进程**。集群只能让契约指向远程实例，编排不得知道节点存在。
- **复合服务与普通服务不可区分**：在注册表、能力面、监督里一视同仁，因此嵌套组合必须天然成立，不需要特判。
- **失败类别属于契约**，不是传输层的字符串；HTTP / CLI / MCP 各自把类别投影成自己的码。

## Consequences

- 契约里不许出现「进程」「端口」「重启次数」这类实现细节。出现一个，复合与远程就要开特判。
- 编排、集群、复合都能用 fake 契约做测试，不必起真实进程；这是测试面最大的收益。
- 契约改动会同时影响四种实现，所以它必须是最保守的那部分：宁可少承诺，也不要为了某个实现加字段。
- 今天散在 `slot`、`package`、`registry` 里的契约要素（能力声明、生命周期义务、健康、失败）要在迁移第 2 步集中，之后才能写编排。
- 需要「某个实现专属」的能力时，只能放进实现内部，不能进契约；否则远程实现永远补不齐。
