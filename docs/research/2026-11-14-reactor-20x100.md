# 20 个 SPK × 100 并发的 reactor 回归（HTTP / SSE / WS / MCP）

> 日期：2026-11-14
> 环境：WSL2 Debian，release 构建，20 个最简 shell `.spk` 插件
> 脚本：`tools/perf/reactor_scale.py`
> 目的：验证 Unix 全 reactor 改造后，连接/插件数量不会把 daemon 线程数线性拉高，并覆盖 HTTP、SSE、WS、MCP 四条面。

## 方法

- 生成一个 shell 插件 fixture：`echo` + `emit` 两个能力、一个 `payload/web/index.html`；
- 用 `plugin bundle` 生成 20 个不同 id 的 `.spk`（`p0`…`p19`）；
- 安装并逐个启动；
- 对每个插件发 100 个并发操作（共 2000 个）：
  - HTTP：`GET /plugin-ui/pN/`；
  - MCP：`POST /mcp`，`tools/call pN.echo`；
  - SSE：`GET /plugin-ui/pN/events`，保持 2 秒；
  - WS：`GET /plugin-ui/pN/ws` 完成握手，保持 2 秒；
- 同时采样 `/proc/<daemon>/status` 的 `Threads`。

脚本是 Python asyncio 客户端，避免用 2000 个 OS 线程做压测客户端。

## 结果

| 面 | 请求/连接数 | 成功 | 失败/拒绝 | 耗时 |
|---|---:|---:|---:|---:|
| HTTP | 2000 | 2000 | 0 | 0.453 s |
| MCP | 2000 | 2000 | 0 | 12.81 s |
| SSE | 2000 | 1280 | 720（429） | 2.279 s |
| WS | 2000 | 1280 | 720（429） | 2.445 s |

daemon 峰值线程数：**10**。

## 解读

- HTTP、MCP、SSE、WS 都跑在 reactor 上；2000 个并发连接没有产生 2000 个线程。
- 峰值 10 线程大约对应：daemon 主线程、插件 reactor、管理 reactor、HTTP reactor、4 个 HTTP worker、管理客户端 reactor、temp cleanup 线程。
- SSE/WS 的 429 不是 reactor 瓶颈，而是每插件 `MAX_SUBSCRIBERS = 64`：20 × 64 = 1280 个成功，剩余 720 个被明确拒绝。这是现有的按插件配额，不是连接泄漏。
- MCP 2000 次全部成功；耗时主要由 4 个 HTTP worker 串行转发管理通道决定，不是连接建立成本。
- 没有出现 `busy`：虽然客户端每个插件并发 100，但 4 个 worker 限制同时在途的调用数，没有把单插件 64 在途上限打满。

## 注意

- 这是 20 个最简 shell 插件、单机 WSL 的合成基准；不是生产容量承诺。
- 客户端并发是 2000 个 asyncio 连接；服务端线程数固定不代表 CPU/队列没有上限。
- Windows 仍走 thread fallback，本结果只代表 Unix。
- 该测试没有覆盖插件自身的耗时（模型/视频生成）或 blob 大对象传输。

## 复现

```bash
cargo build --release
python3 tools/perf/reactor_scale.py \
  --binary target/release/svcd \
  --work /tmp/svcd-reactor-20 \
  --plugins 20 --concurrency 100
```

脚本输出 JSON 并写入 `<work>/results.json`。
