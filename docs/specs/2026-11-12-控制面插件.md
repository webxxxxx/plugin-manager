# 控制面插件：把 HTTP / MCP 移出 svcd

> 状态：草案（2026-11-12），待维护者拍板
> 若采纳，取代 `docs/core-selection-spec.md` 的：§1.6 的 core 能力面、§3.3–§3.6、§16 中 #33/#37/#38/#39/#40/#41 的边界
> 相关：#39（已实现但按本文方向不合并）、#50（plugin bundle）

## 0. 一句话

**svcd 只做「服务监督 + 本地控制通道」；HTTP UI、MCP、LAN 鉴权装进一个可选的签名插件 `control-plane.spk`，插件通过本地控制通道的 RPC 管理 svcd。**

## 1. 为什么

现状把三种东西塞进了 root 守护进程：

| 关注点 | 现状 | 问题 |
| --- | --- | --- |
| 进程监督 / 注册表 / 日志 / 安装信任 | `daemon.rs` / `slot.rs` / `plugin.rs` | 这是 svcd 的本职，应该留下 |
| 网络面（HTTP、登录、cookie、CSRF、LAN token） | `api.rs` / `lan.rs` | 网络攻击面进 TCB；TLS/鉴权永远做不完 |
| 协议面（MCP 聚合、SSE/Streamable HTTP） | `mcp.rs` / 未来的 `/mcp` | 协议演进快，绑定核心发布节奏 |

拆出去的收益：

- 核心二进制更小、TCB 更窄；嵌入式 2 MB 预算更宽松。
- UI / MCP 可以独立发版、按需安装；不用管理界面的人不装。
- svcd 不再监听任何 TCP；默认零网络面。
- 网络鉴权、cookie、CORS、TLS 终止这些「产品决策」归插件，不污染监督语义。

**必须先说清楚它不解决什么**：插件目前和 svcd 一样以 root 运行，控制面插件仍能拿到 `svcd.token`。所以这不是安全隔离，是**模块化 + 发布解耦 + TCB 收敛**。真正的隔离需要受限 token / 非 root 运行，见 §7。

## 2. 目标与非目标

**目标**

- `svcd` 不包含 HTTP listener、HTTP 路由、cookie/LAN 鉴权、MCP 协议实现。
- 控制面插件是一个普通 `.spk`：可安装、可卸载、可启停、有 web UI，通过本地通道管理 svcd。
- 管理语义仍然只有一套：CLI、控制面插件、MCP 都走同一组 daemon RPC。
- core 服务不再作为能力提供者（manifest 不再有 `capabilities`）；core 用 start/stop/status 生命周期钩子做资源申请/释放。
- `svc` 的现有命令保持可用；没有控制面插件时 CLI 仍能完成全部管理。

**非目标（v1）**

- 不做 TLS 终止、多用户/角色、配置加密、svcd 自升级（沿用旧规格 §6 / §13-C5）。
- 不做控制面插件的非 root 沙箱（列为后续）。
- 不做商城；控制面插件先靠 `plugin bundle` 产出、`trust.d` 分发。
- 不保证第三方插件 web UI 的反代；见 §3.3。

## 3. 组件与边界

```
+-----------------------------+         本地 UDS / 命名管道 + token          +--------------------------------+
| svcd (root)                 | <------------------------------------------> | control-plane plugin (root)    |
|                             |          JSON-RPC control v1                 |                                |
| registry / supervisor       |                                              | HTTP :8787 / :80               |
| install / trust / config    |                                              | web UI (payload/web)           |
| logs / local control channel|                                              | /mcp (modern-only)             |
+-----------------------------+                                              +--------------------------------+
        |                                                                             |
        +-- 监督 core 脚本 / plugin 进程 ---------------------------------------------+
```

### 3.1 svcd 保留

- 本地控制通道（旧规格 §3.1 的 JSON-RPC + NDJSON、token、UDS/命名管道）。
- 注册表、依赖图、监督器、日志、安装/验签、配置模板/活动副本/last-good。
- `services.*` / `plugins.*` / `config.*` / `logs.*` 的 RPC 与状态。
- 生命周期钩子的执行与超时。

### 3.2 移出

- `api.rs` 的 listener、路由、错误码映射、下载/上传。
- `lan.rs` 的 token/cookie/CSRF/登录限速/绑定重绑。
- `mcp.rs` 的协议投影与未来 `/mcp`；保留 registry 的 `tools` 语义，作为 RPC 暴露。
- `http.rs` 的 HTTP 原语（随 listener 一起走）。

### 3.3 插件 web UI 的两种形态

v1 只承诺控制面插件自己的 UI：

- 控制面插件在 `payload/web/` 放静态页，由它自己的 HTTP server 提供；登录/会话也由它自己管。
- 其他插件的 `ui` 字段不再由 svcd 反代。要么插件自己监听端口并在控制面 UI 里给链接（参考 `index.html` 的 `url` 字段，`{host}` 替换），要么后续由控制面插件做统一网关。
- `/plugin-ui/{id}` 反代不在 v1 范围内；§3.3 的旧实现本来也只是骨架，删掉成本最低。
- manifest 的 `ui` 字段保留，但语义从「svcd 反代入口」改为「客户端/启动器可打开的 web 入口元数据」；控制面插件自己负责认证与静态文件。

## 4. 控制面契约（control v1）

### 4.1 发现与认证

- svcd 只对 manifest 声明 `control: {"version": 1}` 的插件注入：
  - `SVCD_CONTROL_ENDPOINT`：UDS 路径或命名管道名。
  - `SVCD_CONTROL_TOKEN`：控制通道 token（与 `<config>/svcd.token` 同源）。
  - `SVCD_CONTROL_VERSION=1`。
- 插件启动时先调 `control.info`，版本不匹配就拒绝启动并写 stderr。
- 没有 `control` 字段的插件拿不到这三个变量；但注意 root 插件仍可自己读 token 文件，v1 不防。

### 4.2 方法

| 方法 | 参数 | 返回 |
| --- | --- | --- |
| `control.info` | — | `{control:1, svcd:{version,platform}, features:[...]}` |
| `services.list` | — | `{services:[summary]}` |
| `services.status` | `{id}` | `{summary, details}` |
| `services.start` / `stop` | `{id}` | `{summary}`（start 同步到 ready，超时 504 由插件映射） |
| `services.enable` / `disable` | `{id}` | `{summary}` |
| `services.logs` | `{id}` | `{path, size}`（日志文件路径；插件自己按 `lines` 取 tail 并截到 1 MiB） |
| `plugins.install` | `{path, strategy}` | `{summary}` |
| `plugins.uninstall` | `{id, purge}` | `{ok}` |
| `plugins.import` | `{path, config_id?, no_config?, force?}` | `{id?, version?, state?, configApplied, warnings}` |
| `plugins.export` | `{id}` | `{path, filename, size, sha256}`（临时文件，插件负责删除） |
| `config.get` | `{id}` | `{path, sha256}`（活动副本路径，只读） |
| `config.put` | `{id, path, check:true}` | `{ok}`；校验失败 → `check_failed`（候选文件由调用方写临时区） |
| `config.reset` | `{id}` | `{ok}` |
| `registry.tools` | — | 只含 plugin 能力的 MCP 工具投影；`svc.*` 管理工具由控制面插件自己追加 |
| `registry.call` | `{name, arguments}` | MCP 结果；内部按服务/能力路由 |

约定：

- 所有错误返回 `{code, message, status?}`；`status` 是给 HTTP 的建议码（400/401/403/404/409/413/500/504），插件可以覆盖。
- **大对象一律走临时文件**，控制通道不传 >1 MiB 的 JSON：配置、`.spkb`、日志都返回路径，由插件读/写。候选配置写入 `<data>/tmp/control-*/`，svcd 校验路径前缀后才读取；svcd 启动时清理超过 1 小时的 `control-*`。
- `config.put` 在 RPC 层校验 1 MiB 上限；活动副本仍由 svcd 原子替换 + last-good。
- `plugins.export` 由 svcd 写临时文件，返回 `{path, filename, size, sha256}`；插件读完后删除。
- `services.logs` 返回日志文件路径；控制面插件按行取 tail，再按字节截到 1 MiB（保留尾部、对齐行边界），保证 HTTP 响应 ≤1 MiB。
- `plugins.import` 的错误分类必须与 CLI 相同：`usage` / `check_failed`（409）/ `too_large`（413）/ `conflict`（409）/ `forbidden` / `internal`。这是 #39 review 已经点出的问题，收敛到 RPC 时一次修掉。

### 4.3 长操作与事件循环

- `services.start/stop`、`plugins.install/uninstall` 仍由 daemon 事件循环串行处理（现有语义）。
- `config.put/reset` 会跑 10s 的 `configCheck`，**不能阻塞事件循环**：放到独立的 control worker 线程，事件循环把 `PendingCall.reply` 转交给 worker，继续处理监督事件。
- `plugins.import` 组合 install（事件循环）+ 配置应用（worker），需要在 worker 里串行，避免和 `config.put` 交错。
- 这是本方案唯一新增的并发点；v1 用一个 `Mutex<()>` 串行所有配置写入即可（与 #39 的 `CONFIG_WRITES` 同思路）。

## 5. core 生命周期

### 5.1 manifest

```json
{
  "schema": 1,
  "id": "vpn",
  "version": "1.0.0",
  "desc": "VPN service",
  "exec": { "path": "/usr/local/bin/vpn", "args": [], "ready": "exec" },
  "lifecycle": {
    "start":  { "path": "/usr/local/bin/vpn-script", "args": ["start"],  "timeout": 30 },
    "stop":   { "path": "/usr/local/bin/vpn-script", "args": ["stop"],   "timeout": 10 },
    "status": { "path": "/usr/local/bin/vpn-script", "args": ["status"], "timeout": 5 }
  }
}
```

- `lifecycle` 全部可选；没有就是现在的 `exec` 行为（向后兼容）。钩子 `path` 必须绝对路径。
- 有 `start` 时，**start 命令就是被监督的前台进程**，替换 `exec`（start 优先）；`ready` 仍然生效（默认 `notify`，脚本不讲话就用 `exec`）。
- 明确禁止 `start` 自己 daemonize：脚本应申请资源后 `exec` 真正的进程，或者直接在前台跑。daemonize 会被监督器当成退出。
- `stop` 在 SIGTERM 之前跑，用于释放资源；显式 stop 时即使进程已退出也跑一次（避免资源泄漏），崩溃后不自动跑（避免误释放）；超时/非零只记日志，随后继续现有停止序列（SIGTERM → 10s → SIGKILL → 5s）。
- `status` 由 `svc status` 按需调用；exit 0 = healthy，非零 = unhealthy；不解析 stdout。v1 监督器不做定期轮询，避免引入新的重启语义。
- 钩子环境：清空后只给 `PATH`、`SVCD_SERVICE_ID`、`SVCD_ACTION`（start/stop/status）、`SVCD_DATA_DIR`、`SVCD_CONFIG_DIR`、`SVCD_LOG_DIR`；cwd = 定义文件所在目录；Unix 进程组 kill；Windows 用现有控制帧 + TerminateProcess。

### 5.2 core 不再有 capabilities

- `services.d/*.json` 出现 `capabilities` 直接拒绝加载，错误里给出迁移提示。
- `tools/list` / `tools/call` 只认 plugin 能力；core 不出现。
- 控制面仍然可以用 `svc.start/stop/status` 管理 core——那是**管理面**，不是 core 的能力面。
- `svc.*` 工具由控制面插件提供（通过 `registry.*`），不是 svcd 内建的 MCP。

### 5.3 依赖与 enabled

不变：依赖图、`enabled` sidecar、退避、日志、`svc list/status` 都沿用。

## 6. MCP

- 控制面插件提供 `POST /mcp`（modern-only，2026-07-28），工具 = plugin 能力 + `svc.*` 管理工具。
- 聚合语义仍在 svcd：控制面插件调 `registry.tools` / `registry.call`，自己追加 `svc.*` 管理工具，只做协议翻译。
- `mcp` 第四入口保留为**薄客户端**：stdio ↔ 控制面插件 `/mcp`；插件没装就 stderr 报错 + exit 1。
- core 不参与 `tools/call`；`svc.*` 是管理工具，不是 core 能力。

## 7. 安全

- v1：控制面插件与 svcd 同权限（root/System）；安装它 = 安装一个 root 组件。文档必须写死。
- `control` 字段只是契约声明，不是授权边界；root 插件仍可读 token。
- 后续（v2）：每个控制面插件独立 token + 方法 allowlist（`services.*` 可写、`plugins.*` 可写、`config.*` 可写…）；控制面插件可改为非 root，通过 socket ACL + token 访问。这会改变 `svc` 的组权限模型，单开票。
- 控制面插件自己的 HTTP 鉴权：token/密码文件 + 会话 cookie；**不要**复用 svcd 的控制 token 作为用户密码。LAN 开关、TLS 终止都由插件负责。
- `svc lan` 在 v1 废弃，能力移到控制面插件的配置/UI；保留一个兼容子命令也只做转发。

## 8. 包与发布

```
control-plane.spk
  manifest.json
  signature.json
  payload/bin/control-plane[.exe]
  payload/web/index.html
  config/config            # 可选：监听地址、口令 hash
```

```json
{
  "schema": 1,
  "name": "control-plane",
  "version": "0.1.0",
  "desc": "Web 控制台与 MCP 入口",
  "platform": "x86_64-unknown-linux-musl",
  "protocol": 1,
  "exec": { "path": "payload/bin/control-plane", "ready": "exec" },
  "ui": { "type": "web", "entry": "index.html" },
  "control": { "version": 1 },
  "config": "config/config",
  "files": [ ... ]
}
```

- 旧规格 §2.2 的 manifest 表新增可选 `control: {version}` 字段；未知字段忽略的规则不变。
- 用 #50 的 `plugin bundle` 从目录产出签名 `.spk`；#50 因此是关键前置。
- 平台：为每个目标产出一个包；嵌入式先出 musl x86_64/aarch64/armv7。
- 版本偏斜：插件 `control.version` 高于 svcd 就拒绝启动；低于则按 v1 兼容。

## 10. 风险与未决

1. **两进程故障面**：控制面插件挂了，UI/MCP 不可用，但 CLI 和 svcd 不受影响；需要明确的 `svc plugin start` 恢复路径（参考 UI 已有提示）。
2. **token 传播**：控制插件拿到 svcd token；插件被攻破 = root。v1 接受，v2 收敛。
3. **版本偏斜**：控制面插件与 svcd 的 control 协议版本要显式协商；升级顺序建议先升 svcd 再升插件。
4. **控制通道帧上限**：控制通道保持 1 MiB 帧；大对象（配置候选、`.spkb`、日志）一律走临时文件路径，不进 JSON。这是阶段 1 的硬约束，避免为管理面放宽插件 stdio 的协议上限。
5. **1 MiB 日志响应**：按字节截断，保留尾部；与 #39 review 一致。
6. **import 的 kind/错误码**：core id 的 `.spk` 不能落成 500；在 RPC 层返回结构化错误，插件映射 404/409。
7. **非 root daemon 的 import**：`root_required()` 不能藏进共享 import 路径；权限检查放调用方（CLI 或插件），RPC 只做数据校验。
8. **core 生命周期钩子的语义**：本文按「start 前台 + stop 前置 + status 探针」写；若选 SysV 外部脚本或纯兼容层，§5 要改。
9. **体积收益**：删掉 HTTP/LAN 代码对嵌入式是净收益，但幅度要到阶段 3 实测；不要把「变小」当主要卖点。
