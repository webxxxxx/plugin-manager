## 1. 一句话定位

一个 Rust 写的**单二进制守护进程** `svcd`：看住服务与插件、装插件、把插件的能力通过 MCP 桥暴露给 AI、把插件的网页反代出去。

- 平台：Linux（含嵌入式 / OpenWrt）、macOS、Windows；不含移动端
- 插件只有一种运行方式：**独立进程**
- 插件包：`.spk`，**一个包只装一个目标平台**
- 体积：嵌入式 **≤ 2,000,000 B**；桌面 **≤ 30,000,000 B**

---

## 2. 四个入口，一个进程

需求原文里的「svcd + PluginManager 两个组件」**已经合并**：PluginManager 作为独立进程退役，它的一切（装插件、校验、MCP 聚合、反代）都成为 `svcd` 的内部功能。但**它的命令面保留**——交付物是**一个可执行文件**，安装时建四个硬链接：

| 入口 | 是什么 | 谁来用它 | 类比 |
|---|---|---|---|
| `svcd` | 守护进程本体：服务监督 + 插件管理 + MCP 聚合 + 反向代理 | 系统服务管理器开机拉起 | 工头 + 物业前台，同一个人 |
| `svc` | 命令行：管**任意服务**（core 或 plugin）的 `list / status / start / stop / enable / disable / logs / ui` | 你 | 对讲机：什么都能问 |
| `plugin` | 命令行：**只**管插件，动词与 `svc` 同源，另加 `install / uninstall / editconfig / export / import` | 你 | 前台专线：只办插件，不办别的 |
| `mcp` | stdio 的 MCP 桥，给 AI 客户端当子进程拉起 | AI 客户端（IDE、桌面助手） | 给 AI 用的插座 |

> 四者是**同一个文件**（`argv[0]` 派发）。装不上硬链接时降级为 symlink，再降级为副本并告警。

```
系统服务管理器（systemd / launchd / Windows SCM / BusyBox init）
        │ 开机拉起 + 保活
        ▼
   svcd（唯一的守护进程，也是插件进程的父进程）
        ├── core 服务（svcd 自带或系统级）
        └── plugin 服务（.spk 装出来的插件进程）
                 ▲
     ┌───────────┴───────────┐
  svc（人，管服务）  plugin（人，管插件）  mcp（AI 客户端）
```

## 3. 服务模型（全系统的心脏）

**一切皆服务**，只有两种 `kind`：`core` 与 `plugin`。它们共用**一张注册表、一张依赖图**。

| 概念 | 含义 |
|---|---|
| 生命周期 | `Stopped / Starting / Running / Stopping / Backoff / Failed` 六态 |
| 能力面 | 服务活着才把 manifest 声明的能力放进 `tools/list`；一崩溃立即摘除 |
| 死的服务 | 在可调用面上只剩 `<id>.start`（AI 可以自己把它叫起来） |
| 同源性 | `svc list` 与 `tools/list` 看的是同一张表，不存在两份真相 |
| 启动 | `start` 同步等到 ready 才返回 |
| 依赖 | svcd 解析拓扑序，按层并行启动；上游失败不级联停掉下游 |
| 重启 | 是否自动拉起取决于 **enabled**：enabled 的按退避重试；手动起的崩溃后不自动拉起 |

## 4. 用户看到的行为

### 4.1 `svc` —— 管服务

| 操作 | 说明 | 例子 |
|---|---|---|
| 列表 | 列出所有服务（core + plugin）及状态 | `svc list` |
| 状态 | 单个服务的状态 | `svc status wireguard` |
| 启停 | 启动 / 停止 | `svc start wireguard` / `svc stop wireguard` |
| 自启 | 开机自启开关 | `svc enable wireguard` |
| 开桌面 UI | 桌面构建才有 | `svc ui` |

### 4.2 `plugin` —— 管插件（沿用原需求的命令面）

| 操作 | 说明 | 例子 |
|---|---|---|
| 装插件 | 校验平台与签名、解包、注册为服务 | `plugin install ./wg-1.0.0-x86_64-unknown-linux-musl.spk` |
| 卸插件 | 停服务、删版本、保留配置 | `plugin uninstall wireguard` |
| 列表 | 只列插件（不列 core 服务） | `plugin list` |
| 状态 | 单个插件的状态 | `plugin status wireguard` |
| 启停 | 启动 / 停止（只对插件） | `plugin start wireguard` / `plugin stop wireguard` |
| 自启 | 开机自启开关 | `plugin enable wireguard` |
| 改配置 | 编辑**活动副本**（用户那份） | `plugin editconfig wireguard` |
| 导出 | 只导配置 / 整包 | `plugin export --config-only wireguard` |
| 导入 | 整包或一份配置 | `plugin import ./wg.tgz` |

> `plugin` 只是**另一个启动名**，背后还是同一个 `svcd`，与 `svc` 走同一条本地管理通道；区别只有作用域：它只接受插件 id，传 core 服务 id 会报错「不是插件」。权限模型与 [#19](https://github.com/webxxxxx/plugin-manager/issues/19) 一致。

### 4.3 `svcd` 自己的两种模式

| 命令 | 作用 |
|---|---|
| `svcd run --foreground` | 前台运行，供系统服务管理器拉起 |
| `svcd install-service` / `uninstall-service` | 注册进 systemd / launchd / sc.exe / BusyBox inittab / procd（五份安装计划） |
| `svcd --install [--conf <file>]` / `--uninstall` | 复制四入口并注册服务；`svcd.conf` 可配置 HTTP 端口、LAN 默认开关、plugin/core 路径 |

## 5. `.spk` 包格式

### 5.1 容器与顺序

- **严格 tar，不压缩**（ustar 子集；压缩交给传输层：CDN 的 `Content-Encoding`）
- 条目顺序：`manifest.json` 第一、`signature.json` 第二，其余任意
- 打包可复现：`mtime=0`、`uid/gid=0`、按路径排序、只允许普通文件与目录、末尾两个零块
- 解包拒绝：绝对路径、`..`、反斜杠、链接/设备/稀疏文件、重复路径、清单外条目、setuid；总解压上限 512 MiB

### 5.2 manifest 字段

| 字段 | 必需 | 含义 | 例子 |
|---|---|---|---|
| `schema` | 是 | 清单格式版本 | `1` |
| `name` | 是 | 服务 id（`[a-z0-9][a-z0-9_-]{0,63}`，不含点） | `"wireguard"` |
| `version` | 是 | 语义化版本 | `"1.0.0"` |
| `desc` | 是 | 一句话描述 | `"WireGuard VPN"` |
| `platform` | 是 | **目标三元组**（取代 `arch`） | `"x86_64-unknown-linux-musl"` |
| `protocol` | 是 | 插件协议版本，当前 `1` | `1` |
| `exec` | 是 | 怎么启动：`{path, args?, env?, ready?}` | `{"path":"payload/wg","ready":"notify"}` |
| `config` | 否 | **配置文件在包内的相对路径**，缺省是包根 `config` | `"config"` |
| `dependencies` | 否 | 依赖哪些服务 id | `["net-base"]` |
| `capabilities` | 否 | 能力声明（取代原 `tools`） | `[{"name":"up","desc":"…","inputSchema":{…}}]` |
| `ui` | 否 | 界面：`{type, entry?}`，`entry` 默认 `index.html` | `{"type":"web","entry":"index.html"}` |
| `files` | 是 | 除两个清单外的全部文件：`{path,size,sha256,mode}` | — |
| `hooks` | 否 | `{postInstall?, preRemove?}`，指向 `hooks/` 内可执行文件 | — |

> `platform` 与构建时的 `TARGET` **精确相等**，安装与加载各校验一次。文件名仍是 `<name>-<version>-<arch>.spk`，其中 `arch = platform.split('-')[0]`。

### 5.3 签名

- 包内 `signature.json`：`{alg:"ed25519", keyId, sig}`，签的是 `manifest.json` 的**原样字节**（不做 JSON 规范化，打包器固定序列化只为可复现）
- `files[]` 钉住每个文件的 sha256/size/mode → 逐文件校验后才能落盘
- 信任根：编译期内置 store 公钥 + `/etc/svcd/trust.d/<keyId>.pub`（**PEM SPKI**）；未知 keyId 直接拒；**没有 `--insecure`**

### 5.4 安装策略

| 策略 | 默认场景 | 行为 |
|---|---|---|
| `keep-old` | 桌面 | 新版本并存 → fsync → rename → 切 `current`；留一份旧版本可回滚 |
| `replace` | 嵌入式（空间小） | 验签 → 停服务 → **先删旧版本腾空间** → 解包 → 切 `current`；失败不留半装，回滚 = 重装旧包 |

空间不足时自动降级为 `replace`。布局：`/var/lib/svcd/plugins/<id>/<version>/` + `<id>/current`（版本号文本）+ `<id>/enabled`。

### 5.5 hooks

- 只接受 `hooks/` 下的**可执行文件**（不解析内联 shell）
- 60 秒超时；环境只给 `PATH` 与 `SVCD_*` 变量
- 嵌入式**默认拒绝**带 hooks 的包（`--allow-hooks` 放行）
- 权限 = 安装者权限，信任只来自签名

## 6. 配置流（本轮新增，细节在 #20）

把插件「**会变的部分**」从只读的 payload 里拎出来，让用户能改：

```
包内 config（模板，只读，被签名覆盖）
      │ 安装时复制
      ▼
活动副本（用户可编辑，不在签名范围内）
      │ editconfig 编辑它；启动时以它为准
      ▼
运行中的插件进程
```

四条已明确：

1. `manifest.config` 指向包内相对路径，缺省是包根目录的 `config`。
2. 安装时复制成**活动副本**，`plugin editconfig` 编辑活动副本，不是包内模板。
3. `plugin export --config-only` 只导配置；`plugin export` 导整包（含当前配置）；`plugin import` 按文件内容判断。
4. 升级**保留**用户配置（建议，待 #20 确认合并规则）。

> 活动副本放哪、属主与权限、改坏了怎么回退 —— 归 [#20](https://github.com/webxxxxx/plugin-manager/issues/20)，其中权限部分与 [#19](https://github.com/webxxxxx/plugin-manager/issues/19) 联动。

## 7. IPC 与 MCP

### 7.1 一条信封，三种通道

**JSON-RPC 2.0 + NDJSON**（一行一条），同一套帧跑：

- 子进程 **stdio**（默认控制通道）
- **UDS / 命名管道**（Windows）
- **`POST /plugin-ui/{id}/rpc`**（浏览器里的插件 UI 调回宿主）

约束：帧上限 **1 MiB**、在途 **64**、超时 **30 s**。方法集：`svcd.ping`（就绪探针）、`tools/call`、`svcd.status`、`svcd.shutdown`。`manifest.protocol` 不是 `1` 直接拒绝安装，**没有握手**。

UI 形态：插件**不自起 HTTP**，静态资源在包里，由 svcd 反代；`/rpc` 用 path-scoped cookie + Origin 校验。

### 7.2 MCP 桥

- 协议面全在 `mcp` 入口；`svcd` 内部只给 `registry.tools` / `registry.call` / `svc.*`
- **dual-era**：modern（2026-07-28：`server/discover` + `_meta` 校验 + `resultType`）与 legacy（`initialize`，支持到 2025-11-25）两个分支
- 热插拔可见性：modern 用 `listChanged:false` + `ttlMs:1000`；legacy 用 `listChanged:true` + 1 秒轮询；**不做** `subscriptions/listen`
- 工具名对外是 `<服务名>.<能力名>`；执行失败一律 `isError:true`，未知工具 `-32602`
- `inputSchema` **透传不校验**（显式偏离规范，校验责任在插件）

## 8. 监督与系统集成

- 六态状态机，事件带 pid，迟到事件直接丢
- 退避：曾在 Running ≥10s → 清零立即重启；否则 `1/2/4/8/16/30s`；连续 5 次进 `Failed`，只有显式 `start` 才复位
- 停止：`SIGTERM` 10s → `SIGKILL` 5s；关机预算 30s
- 就绪：probe-on-spawn，30s 超时
- 不设 finish 脚本，`permafail` 由 `Failed` 终态取代
- OSAL = **5 个边界、0 个 trait**：`proc` / `wait` / `channel` / `install` / `webview`

## 12. 请你点头的 3 个点

### 12.1 PluginManager 作为独立进程退役（对原始需求的最大偏离）

原文：「核心是 svcd 服务管理器与 PluginManager 插件管理器」，两个组件。现在：**只有 svcd 一个守护进程**，插件管理是它的内部功能；命令面是 `svc`（管服务）与 `plugin`（管插件），MCP 面是 `mcp`。

- 理由：PM 与 svcd 的职责在「谁拉起插件、谁持有 IPC、谁做重启」上必然重叠；合并后一张注册表、一张依赖图、一份体积。
- 代价：PM 不再是独立进程/服务；但**命令名 `plugin` 保留**，用户视角的命令面与原文一致。

> **请确认**：接受「一个守护进程 + 四个入口」，还是要求 PluginManager 重新成为独立进程。

### 12.2 `config` 字段的落点

已写进 manifest 与配置流（第 6 节），但**活动副本放哪、权限怎么定、升级怎么合并**要拍 —— 在 [#20](https://github.com/webxxxxx/plugin-manager/issues/20)。

> **请确认**：活动副本放在插件数据目录下（如 `<data>/plugins/<id>/config/`），而不是系统 `/etc`，对吗？
