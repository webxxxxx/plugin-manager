# Protocol 3 raw：20 插件 × 50 WebSocket 512 KiB 连续 60 秒

日期：2026-11-16（初版）／2026-11-16（reactor 化后重测）  
平台：WSL2 Debian Linux x86_64  
构建：`cargo build --release`，默认 `MEM_LEVEL=high`  
连接：20 个 WebUI 插件，每个 50 条 WebSocket，共 **1000 条**  
数据：每条 WS 连续发送 512 KiB binary frame，经插件原样 echo

## protocol 3 格式

插件 stdin/stdout 使用 8 字节头：

```text
u32 payload_len (big endian)
u32 stream_id   (big endian)
payload
```

- `stream_id` 由 daemon 为每条 UI WebSocket 分配；
- 插件必须原样回传 `stream_id`；
- daemon 收到响应后释放 in-flight 预算；
- plugin 声明 `protocol: 3`、`exec.ready: exec`、不能声明 JSON-RPC capabilities；
- UI raw 路由：`/plugin-ui/{id}/{token}/raw`，只接受 binary frame。

## 架构：raw I/O 在 reactor 内

初版每个 raw 插件两条阻塞线程（writer + reader），20 个插件 40 条线程，daemon 总线程 70。

现在 [src/reactor.rs](src/reactor.rs) 的 `svcd-reactor` 单 poll 线程同时拥有：

- notify/exec 插件的 stdout/stderr；
- raw 插件的 stdout（8 字节头 + payload 解析后按 `stream_id` 投递）；
- raw 插件的 stdin（`RawOutQueue` 里的帧，`POLLOUT` 时写，部分写保留 offset）；
- raw 插件的 stderr（日志源）；
- 一个 self-pipe，用于命令与 `RawOutQueue` 的即时唤醒，避免 50ms poll 超时延迟。

背压路径：`ws_inflight_bytes` / `ws_inflight_requests` 限全局在途字节与请求数；
`ws_raw_queue` 限单个插件的待写帧数；慢插件的帧留在 `RawOutQueue` 而不是阻塞线程。
所有失败分支都归入 [src/rawhub.rs](src/rawhub.rs) 的 `RawFailure` 计数（按 2 的幂打日志，
daemon 退出时打 `svcd: raw stats: ...` 汇总）。

Windows 没有可 poll 的匿名子管道，因此保留“每插件两条线程”的旧路径，`/raw` 路由
显式返回 `501 not_supported`（不是静默 404）。

反而略低，线程数降到 1/7，错误归零。调优过程留痕：刚切到 reactor 时只有

才能喂完，而一轮又把某个插件的 stdout 读得太狠。加上「先喂 stdin 再收
stdout」、每轮每插件读预算 256 KiB、把 stdin 管道调到 512 KiB、以及整帧交付
不再二次拷贝之后恢复到 145～170 MB/s。最终二进制上 6 次 60 秒运行全部
`errors=0`、`ws_open=1000`、`data_ok=done`、`daemonThreadsMax=10`。

## 58 个连接错误的根因

初版把 58 个错误笼统记成“连接错误”。加分类后，先在原始架构上跑了一次 60 秒，
拿到真实分布（客户端侧 `error_reasons` + daemon 侧 `svcd: raw ...` 行）：

```text
client  error_reasons      {"EOF": 62, "BrokenPipeError(32, 'Broken pipe')": 1}
client  数据校验失败        2（data_ok 比 done 少 2）
daemon  raw ws closed     62，全部 reason=protocol error
        ├─ reserved frame bits            56
        ├─ client frames must be masked    4
        └─ invalid control frame           2
daemon  RawStats           无 writer_queue_full / subscriber_full / budget_* /
                           plugin_write_error / stream_conflict
```

也就是说：58（另一次运行 101）个错误里**没有一个是 raw 队列、预算或插件 EOF**，
全部是同一个 WS 分帧问题。逐字节诊断：

```text
svcd: raw ws closed: plugin=p06 stream=300 reason=protocol error: reserved frame bits
  buffer=6 read=2621516 parsed=2621510 frames=5 head=a6 79 44 27 a6 79
```

`read == parsed + buffer.len()`，`parsed` 正好是 5 个完整帧（5 × 524302 字节），
剩下的 6 字节是 `mask(4) + 2 字节被掩码的 payload`。结论：

1. **压测客户端把 pong 插进了正在写的数据帧中间**。每条连接分多次 `send()`
   发送 512 KiB 帧；收到服务端 ping 时立刻 `sendall(pong)`，pong 字节就落进了
   未发完的数据帧里。RFC 6455 只允许控制帧出现在帧边界（或分片之间），
   所以 daemon 判定 `reserved frame bits` 是正确的。
2. 这些连接里还有 2 条被 daemon 当成正常帧接收，payload 里混了 pong 字节，
   所以 `data_ok` 差 2。
3. daemon 侧确有一个真 bug：协议错误时把 close 帧 append 到 `connection.out`
   后立刻丢弃连接，未写完的 512 KiB echo 与 close 帧一起被丢掉，客户端只看到
   EOF（分布里的 62 个 EOF 就是这么来的，而不是 close 帧）。现在
   `close_and_flush` 会保留连接直到 close 帧写完（[src/api.rs](src/api.rs)），
   集成测试 `plugin_ui_raw_reports_protocol_errors_with_a_close_frame` 固定这一点。

修复：压测脚本把 pong 排队到帧边界再发；daemon 改为先 flush close 帧再关闭；
WS 写失败、插件 stdout 读失败、插件 stdout EOF 等分别计入 `RawStats`
（`ws_write_error`、`plugin_read_error`、`plugin_eof`），daemon 退出时打
`svcd: raw stats: ...`。之后 `errors=0`、`data_ok` 与 `done` 完全一致。

## 日志检查

`data.log` 63 行，daemon stderr / `svcd.log` 没有：

```text
panic
overflow
fatal runtime
aborted

```

daemon 退出时 `svcd: raw stats: plugin_eof=20` —— 只有停机时 20 个插件的 stdout
EOF，运行期间没有任何 `writer_queue_full`、`budget_*`、`subscriber_*` 或
`plugin_write_error`。正常断开（客户端关连接）不会写日志；只有协议错误、读写
失败、close 帧发送失败和插件侧 EOF 会落一行 `svcd: raw ...`。

## 当前结论

- protocol 3 raw 在 Unix 上是生产路径：单 reactor 线程、明确背压、失败分类可观测。
- 1000 连接 60 秒：`ws_open=1000`、`errors=0`、`data_ok=全部`、无 fatal 标记。
- Windows 的 `/raw` 一律返回 `501 not_supported`（`ws_raw_enabled=off` 时 403），
  且该判断在 web 资源查找之前，所以没有 `ui` 的 protocol 3 插件也不会退化成 404。
  协议 3 插件在 Windows 上仍可启动：stdio 走线程 fallback、stderr 进日志，
  但因为没有客户端能订阅它，这条路径只保证服务能跑起来、日志能看到。

## 复现

脚本：本地基准脚本（不提交到仓库）  
插件 agent：

```python
import struct, sys
source = sys.stdin.buffer
sink = sys.stdout.buffer
while True:
    h = source.read(8)
    if len(h) < 8:
        break
    length, stream = struct.unpack("!II", h)
    payload = source.read(length)
    if len(payload) < length:
        break
    sink.write(struct.pack("!II", length, stream))
    sink.write(payload)
    sink.flush()
```
