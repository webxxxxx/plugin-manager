# 只开 WebSocket 的插件：三档预算各能同时跑多少个（WSL2 实测）

前一张表压的是「五面全开」的插件（invoke / SSE / WebSocket / upload / download）。
这次只留一面：**每个插件一条常驻 WebSocket 连接、同一时刻一个在飞请求（单并发）**，
问的是同一个问题——50 MB、512 MB、2 GB 三档预算，各自能装多少个这样的插件、同时跑起来。

## 方法

- WSL2 / Debian，8 vCPU，5.8 GiB 内存，Python 3.11；daemon 是 `v0.1.2` release 构建，
  `cpu_budget_percent = 90`。
- 夹具是 [budget_scenario.py](../../tools/perf/budget_scenario.py) 里那个 bash NDJSON agent，
  每个插件实例一个进程；另跑一组真包 `samples/spk-tests/ws-panel`（Python，自带每秒 tick）做对照。
- 每个插件的连接就是它自己的 web UI 会开的那条：
  `POST /api/v1/plugins/<id>/ui-token` 铸 token，`GET /plugin-ui/<id>/<token>/ws` 拿 101，
  之后每 1 s 在这条 socket 上发一个 `tools/call`，收到结果才发下一个——**任何时刻每个插件只有 1 个在飞请求**。
- 判据只有一条：N 条连接全部 101、所有调用都成功、没有 timeout / 断链。差一条就算这一档装不下。
- 每 2 s 采一次 daemon 自身（RSS / 线程）与整棵进程树（PSS / RSS / 进程数）。

```sh
python3 tools/perf/ws_plugin_capacity.py \
  --binary /tmp/wt-1012-target/release/svcd \
  --budget 50mb --plugins 288 --duration 20 --think-ms 1000 \
  --work /tmp/ws-cap-50mb-288 \
  --out .scratch/ws/50mb-288.json --report .scratch/ws/50mb-288.md
```

## 三档结果

| 预算 | workload | max_connections | **100% 成功的插件数** | 再上一个点 | daemon RSS 峰值 | daemon 线程 | 进程数 | 整树 PSS | 整树 RSS | p50 / p99 |
| ---: | --- | ---: | ---: | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 50 MB | tiny | 405 | **405** | 406 个：1 条 503 | 34.3 MB | 7 | 406 | 145.2 MB | 1378 MB | 7.5 / 176.0 ms |
| 512 MB | interactive | 421 | **421** | 422 个：1 条 503 | 35.8 MB | 11 | 422 | 150.9 MB | 1432 MB | 13.8 / 83.5 ms |
| 2 GB | streaming | 797 | **797** | 798 个：1 条 503 | 64.2 MB | 19 | 798 | 280.9 MB | 2708 MB | 17.5 / 218.5 ms |

（这三行是 2026-11-21 重新标定之后的值：基线 32 MiB → 8 MiB，连接槽加 80 KiB 实测下限，
所以三档的名额从 288 / 399 / 786 抬到 405 / 421 / 797。标定前的原始测量见下面「重新标定」一节。）

三档的「100% 成功的插件数」都**正好等于派生的 `max_connections`**：一个插件一条常驻 WS，
一条 WS 就是一个连接名额，405 / 421 / 797 是什么数，插件就是多少。

再往上的那一个点，拒绝形态固定：第 N+1 个插件挂在 `POST /api/v1/plugins/<id>/ui-token` 或 WS 握手上，
返回 **503（准入拒绝）**，不是超时、不是 429；已经建立的 N 条连接照旧 100% 成功。

## 内存不是约束，连接数才是

| 档 | daemon RSS | 占预算 | 每插件 daemon 成本（扣 3.4 MB 基线） | daemon CPU 峰值 |
| ---: | ---: | ---: | ---: | ---: |
| 50 MB | 34.3 MB | 69% | 78 KB | 4.4% 单核 |
| 512 MB | 35.8 MB | 7.0% | 77 KB | 6.2% 单核 |
| 2 GB | 64.2 MB | 3.1% | 76 KB | 14.6% 单核 |

每个插件（注册表项 + 一条常驻连接 + 它的订阅）在 daemon 里约 **77 KB**，三档一条直线；
正是这条斜率让人可以按连接数而不是按内存估算。50 MB 档跑满 405 个用掉 69% 预算，
`worst_case` 规划值仍然贴着 50 MB（涨价来自连接槽的实测下限，不是泄漏）。

整棵树是另一回事：bash 夹具每个实例约 3.4 MB RSS（且共享页各算一次），405 个 1.38 GB、
797 个 2.71 GB。预算不管插件进程，这一列只是提醒「50 MB 的 daemon 可以带起 1.4 GB 的插件树」。

## 边界与两个容易误判的点

- **512 MB 档第一次跑 399 只开了 398**：第 399 个插件的 WS 握手拿到一条 503。原因是
  `/ui-token` 那次 POST 自己也要占一个连接名额，收尾与握手在同一个槽位上撞了一次；重跑一次就是
  399/399 全过（上表用的是重跑数据），再往上到 400 个才稳定出现 1 条拒绝。这是边界抖动，
  不是 398 的上限。
- **256 个页面 token 的上限不挡这个场景**：token 只在握手时校验
  （`src/face/plugin_streams/mod.rs` 的 `admit` → `src/face/plugin_ui.rs` 的 `valid_token`），
  `plugin_tokens` 满了会驱逐最早的一条（`src/server/auth/lan.rs`），但已建立的连接不受影响，
  所以 786 个插件可以各自握手成功。真实后果在另一处：**超过 256 个插件 UI 同时重连时，
  先重连的那批会拿到 401**——这是页面 token 的容量，不是连接的容量。
- **线程数与 CPU 都不按连接涨**：288 条连接 7 线程、399 条 11 线程、786 条 19 线程（Unix 是
  poll 循环 + 少量 blocking 线程，不是每连接一线程）；786 条连接每秒 786 次调用，daemon 峰值
  只占 14.6% 单核。三档都是准入先到顶，不是 CPU 或线程先到顶。

| 项 | 值 |
| --- | ---: |
| 连接 | 32/32，全部 101 |
| 调用 | 640/640 成功 |

## 想装更多：为什么只有这么点，以及三条实测杠杆

三档的数字不是「机器只扛得住这么多」，而是**预算按最坏情况记账**的结果。把每档的预算拆开：

| 档 | 固定项（基线 32 MiB + 队列 + 环 + inflight + 线程栈） | 每个连接槽记账 | 槽数 | 实测 daemon RSS |
| ---: | ---: | ---: | ---: | ---: |
| 50 MB | 40.7 MB（81%），其中 32 MiB 基线占 64% | 33.9 KB = 单体 25.6 KB + 2×流缓冲 4 KB + 128 B | 288 | 25.8 MB |
| 512 MB | 87.9 MB（17%） | 1.06 MiB = 单体 1 MiB + 2×32 KB + 128 B | 399 | 34.2 MB |
| 2 GB | 278.5 MB（14%） | 2.25 MiB = 单体 2 MiB + 2×128 KB + 128 B | 786 | 63.3 MB |

关键在「单体」这一项：`max_complete_body_bytes` 是**按预算派生**的（50 MB → 25.6 KB，
512 MB → 1 MiB，2 GB → 2 MiB），而一个 WebSocket UI 每帧只有几百字节到几 KB。
预算是给「最坏情况下一个请求能有多大」留的钱，所以**实际 RSS 只有预算的 5%–52%**，
剩下的全是没被用到的预留。

实测三条杠杆：

| 做法 | 命令要点 | 结果 |
| --- | --- | --- |
| 钉住单体，不让它随预算涨 | `max_complete_body_bytes=8192`（50 MB 档被地板抬到 16 KB） | 50 MB：288 → **396** 条，100% 成功，RSS 48.1 MB |
| 同上，512 MB 档（改动前） | `max_complete_body_bytes=65536` | 派生 `max_connections=3389`，但撞上当时的 **1024 流上限**，实测只开 1024 条（1200 个插件里 176 个 503），RSS 93.9 MB |
| 提高预算 | `--budget-percent 90`（4.46 GiB）+ `tiny` | **1000/1000** 全开，派生 1459 槽，RSS 78.8 MB |

三面墙的先后顺序（撞到一个就停）：

1. **预算派生**：`每槽记账 = 单体 + 2×流缓冲 + 128 B`，单体随预算涨，所以 50 MB 是 288、2 GB 是 786；
2. **流上限**（`STREAM_CEILING`）：一条 WS 是一个流，钉住单体后连接数可以到 3389，而当时流还是 1024；
3. **连接上限 4096**（`MAX_CONNECTIONS_CEILING`）：到顶后不论预算多大都只有 4096 条；
4. **插件进程内存**（本机真上限）：bash 夹具 3.4 MB/个，5.2 GiB 可用内存 ≈ **1500 个**。
   实测 50 MB 预算 idle 装 800 个：800/800 运行，daemon 60.3 MB、整树 2.65 GB；1200 个时整树 4.1 GB。
   连接数给得再多，这一层也过不去。（流上限已按下一节改动提到 4096。）

所以「插件数还能提升」的路径按性价比排：

- **配置层**（不写代码）：把 `max_complete_body_bytes` 钉到真实需要的大小，同时显式给
  `max_connections` / `max_streams`；WS UI 用 32–64 KB 单体就够，别让 1–2 MB 的预留白占槽位。
  用不上的队列也可以收：`pending_queue`、`progress_queue`、`ws_raw_queue`、`ws_raw_max_bytes`。
- **预算层**：`mem_budget_percent` 提到可用内存的 80%–90%，让 32 MiB 基线摊薄；
  注意单体也会随之变大（这是上面那张表里 512 MB / 2 GB 档每槽变贵的原因），所以要配合第一条一起调。
- **插件层**：把 3.4 MB/个降下来（编译型插件、共享运行时、少起进程），本机上限才能从 ~1500 往上走。
- **代码层（最大单点收益）**：`RESIDENT_BASELINE_BYTES` 是写死的 32 MiB 预留（`src/platform/limits/specs.rs`），
  而实测 idle daemon 只有 3.4 MB。它单独就吃掉 50 MB 预算的 64%；若改成按预算比例或可配置，
  50 MB 档仅这一项就能多出 **约 990 个槽**（32 MiB ÷ 33.9 KB）。
- **架构层**：一个插件一条连接是当前 UI 的形态（协议 3 raw hub 已经在**单个插件内部**用 `stream_id` 多路复用，
  跨插件复用需要新增一条 console 级多路复用路由）。做到之后插件数就不再等于连接数，
  上限回到「进程内存」那一层。

## 改一版：把插件数顶到本机上限

两处改动（`src/platform/limits/`）：

- `STREAM_CEILING` 从 1024 提到 `MAX_CONNECTIONS_CEILING`（4096），`MAX_STREAMS` 的键上界同步到 4096。
  理由是一条 WS 就是一个流：插件 UI 面板每个占一条，流上限压在 1024 时，连接预算再大也只能兑现 1024 条——
  正好卡住「很多插件 UI」这种主场景。
- 单请求体与预算解耦（配置层，不写代码）：`max_complete_body_bytes` 钉到 64 KiB，预算交给槽位。
  派生把 `单体` 当成每连接成本，而 UI 帧只有几百字节，不钉住它就是在给永远不会发的包留钱。

实测（同一台 WSL：8 vCPU / 5.8 GiB）：

| 配置 | 派生槽位 / 流 | 实际同时运行 | daemon RSS | 整树 RSS |
| --- | ---: | ---: | ---: | ---: |
| 512 MB + 单体 64 KiB（改前：流上限 1024 卡死） | 3389 / **3389** | **1100 / 1100** | 87.1 MB | 3736 MB |
| 90% 预算（4.34 GiB）+ 默认派生 | 1459 / 1459 | **1300 / 1300** | 101.6 MB | 4412 MB |
| 90% 预算（4.45 GiB）+ 单体 64 KiB | **4096 / 4096** | **1400 / 1400** | 108.9 MB | 4745 MB |

三组都是 100% 成功（每个连接都 101，所有调用都有结果，没有 503/超时）。

**现在卡在哪**：不是 daemon，是插件进程本身。bash 夹具每个 3.39 MB，5.1 GiB 可用内存 ≈ **1500 个**；
1400 个已经把整树推到 4.7 GB。daemon 侧 1400 条连接只用了 108.9 MB，4096 个槽位还空着 2/3。
要在这台机器上再多，只有两条路：插件更便宜（编译型 / 共享运行时），或者换更大的机器。

50 MB 档没有跟着变多，原因是另一个：32 MiB 的固定基线（`RESIDENT_BASELINE_BYTES`）占掉预算的 64%，
而实测 idle daemon 只有 3.4 MB。这一项的替换写在 `specs.rs` 的注释里（#107「measured baseline」），
属于要重新标定不变量的活：不是简单调小常量——实测每条连接的真实占用约 78 KB，比账面 34 KB 高，
两者要一起重算，否则账面上放得下、物理上放不下。

配好这一版的 `svcd.conf` 片段：

```ini
mem_budget_percent = 90
workload = tiny
max_complete_body_bytes = 65536
```

复现：

```sh
python3 tools/perf/ws_plugin_capacity.py --binary /tmp/wt-1013-target/release/svcd \
  --budget-percent 90 --workload tiny --plugins 1400 --duration 20 --think-ms 1000 \
  --config max_complete_body_bytes=65536 \
  --work /tmp/ws-max-1400 --out .scratch/ws/max-90pct-64k-1400.json
```
## 重新标定：基线 32 MiB → 8 MiB，连接槽加实测下限

上面三档原来是 288 / 399 / 786，卡在两边都不真实的记账上：

- **常驻基线 32 MiB** 是设计时的猜测（`specs.rs` 的注释写着「a measured baseline replaces it in #107」）。
  参考机上空载、无插件的 daemon 实测只有 **3.4 MiB**，32 MiB 在 50 MB 预算里独占 64%。
- **连接槽只记「单体驻留 + 流缓冲」**（tiny@50 MB 是 29 KiB），而实测每条连接连带它那条插件监督项是
  **75–77 KiB**——账面比物理低一半，于是「账面放得下」不等于「物理放得下」。

实测（50 MB 预算、bash 夹具、每插件一条 WS）：

| 插件 | daemon RSS | 每插件 |
| ---: | ---: | ---: |
| 100 | 11.7 MB | 85 KB |
| 200 | 19.3 MB | 81 KB |
| 300 | 26.7 MB | 80 KB |
| 396 | 33.7 MB | 78 KB |

边际成本 75–77 KB/插件，一条直线；空载基线 3.4 MB。于是：`RESIDENT_BASELINE_BYTES` 32 MiB → **8 MiB**
（实测两倍余量），连接槽成本取 `max(单体 + 流缓冲, 80 KiB)`。两条一起生效后：

| 预算 | 名额（标定前 → 后） | 100% 成功（实测） | daemon RSS |
| ---: | ---: | ---: | ---: |
| 50 MB | 288 → **405** | 405 / 405 | 34.3 MB |
| 512 MB | 399 → **421** | 421 / 421 | 35.8 MB |
| 2 GB | 786 → **797** | 797 / 797 | 64.2 MB |
| 4.7 GiB / interactive | 429 → **431** | 432 条探测：431 接纳 / 449 拒绝 | – |

40 个插件、五面同时压（每插件 P 个客户端）也跟着上移：

| 预算 | 100% 成功的最大并发 | 总客户端 | ops/s | p50 / p99 | 再往上 |
| ---: | ---: | ---: | ---: | ---: | --- |
| 50 MB | 每插件 12 | 480 | 1305 | 207 / 756 ms | P=13（520）：113 × 503 |
| 512 MB | 每插件 13 | 520 | 1246 | 218 / 831 ms | P=14（560）：3 × 503（边界抖动） |
| 2 GB | 每插件 ≥26 | ≥1040 | 1199 | 215 / 913 ms | 客户端 in-flight 封顶 ≈ 500 |

标定前同一套测试的 50 MB 是每插件 8 并发（320 个客户端），512 MB 是 12（480）——
也就是说 50 MB 档的并发上限提高了 50%，与名额 288 → 405（+41%）一致。
## 配置档复测：`mem_budget_percent = 90` + `tiny` + 64 KiB 单体

这一档的配置：

```ini
mem_budget_percent = 90
workload = tiny
max_complete_body_bytes = 65536
```

先说一个容易踩的坑：**50 MB 档上这行单体配置会被忽略**。`max_complete_body_bytes` 的上界是
「份额 × 预算」，50 MB 只允许到 25,600 B，写 65,536 会按规则回落到形状值并在派生报告里记一条
`above-upper-bound`（实测 `configured 65536 / effective 25600`）。所以 50 MB 那一行与默认档完全一致；
512 MB 与 90% 档才会真正按 64 KiB 记账。

派生值（同一份配置）：

| 档 | 预算 | 名额 / 流 | 单体 | 流缓冲 |
| --- | ---: | ---: | ---: | ---: |
| 50 MB | 50 MB | 405 / 405 | 25,600（请求的 65,536 被拒） | 4 KB |
| 512 MB | 512 MB | 3590 / 3590 | 65,536 | 32 KB |
| max | 4.65 GB（90%） | 4096 / 4096（上限） | 65,536 | 297 KB |

**40 个插件、五面同压（50 MB，每插件 P 个客户端）**：

| 每插件并发 | 总客户端 | ok / 请求 | peak in-flight | ops/s | p50 / p99 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10 | 400 | 25362 / 25362 | 374 | 1257 | 196 / 689 ms |
| 11 | 440 | 24705 / 24705 | 407 | 1219 | 208 / 828 ms |
| 12 | 480 | 17560 / 17560 | 425 | 863 | 251 / 1414 ms |
| 13 | 520 | 21464 / 21464 | 458 | 1053 | 232 / 1040 ms |
| 16 | 640 | 15591 / 15591 | 384 | 767 | 254 / 1045 ms |

这一轮 P=10…16 都是 100%：名额 405 是**同时连接的准入上限**，而这套混合负载每次请求只有 ~1 ms，
客户端的 in-flight 峰值只到 380–460，所以顶着名额跑也不会必然撞 503。但边界很依赖突发：
同一档 P=8 的一轮出现过 3 个 503，标定前那轮 P=13 出现过 113 个 503。**要稳，50 MB 档按每插件 12、
总 480 个客户端规划**；P 再往上吞吐反而掉（客户端一个 GIL 排队，p99 到 1.4 s）。

**三档的 WebSocket 插件数（每插件一条常驻 WS）**：

| 档 | 名额 | 实测同时运行 | daemon RSS | 再往上 |
| --- | ---: | ---: | ---: | --- |
| 50 MB | 405 | **405 / 405**（请求 421，16 个 503） | 35.5 MB | 准入拒绝 |
| 512 MB | 3590 | **1400 / 1400** | 108.9 MB | 内存（bash 夹具 3.39 MB/个） |
| max（90%） | 4096 | **1400 / 1400** | 108.9 MB | 内存，不是名额 |

512 MB 与 max 两档的准入名额（3590 / 4096）都远高于实测值：卡住的是插件进程本身，
1400 个 bash 插件已经吃掉 4.7 GB；这台 5.8 GB 的机器上限约 1500 个。
## 结论

- 三档能同时跑的 WebSocket 插件数：**50 MB → 288、512 MB → 399、2 GB → 786**，全部 100% 成功；
  再上一个就是一条 503，不是超时。
- 换算关系简单：一条常驻 WS = 一个连接名额 = 约 77 KB daemon 内存；插件进程本身的 3.4 MB
  （bash）不算在预算里。
- 想在这一层再加容量，调的不是插件数而是记账：钉住单体、提预算、轻插件、降基线，见上一节。

## 复现

```sh
# 构建（WSL 内，Linux 文件系统上）
CARGO_TARGET_DIR=/tmp/wt-1012-target cargo build --release --bin svcd

# 三档各自的满额点与越线点
for spec in "50mb 288" "50mb 289" "512mb 399" "512mb 400" "2gb 786" "2gb 787"; do
  set -- $spec
  python3 tools/perf/ws_plugin_capacity.py --binary /tmp/wt-1012-target/release/svcd \
    --budget $1 --plugins $2 --duration 20 --think-ms 1000 \
    --work /tmp/ws-cap-$1-$2 \
    --out .scratch/ws/$1-$2.json --report .scratch/ws/$1-$2.md
done

# 真包：ws-panel，32 个，50 MB
python3 tools/perf/ws_plugin_capacity.py --binary /tmp/wt-1012-target/release/svcd \
  --budget 50mb --plugins 32 --duration 20 --think-ms 1000 \
  --fixture samples/spk-tests/ws-panel --capability status \
  --work /tmp/ws-panel-32 --out .scratch/ws/50mb-32-panel.json
```

`--plugins` 是「装几个、开几条连接」，`--think-ms` 是同一条连接上两次调用的间隔（单并发就靠它：
上一个没回来不会发下一个）。退出码 0 表示这一档 N 个全过，2 表示有拒绝或错误——脚本可以直接当
容量门禁用。
