# 20 个 WebUI 插件 × 50 WebSocket：1 分钟压测

日期：2026-11-16  
平台：WSL2 Debian Linux x86_64  
构建：`cargo build --release`，默认 `MEM_LEVEL=high`  
时长：60 秒  
连接：20 个插件，每个 50 条 WebSocket，共 **1000 条**

## 测试配置

为容纳 1000 条连接，测试用 `svcd.conf` 覆盖：

```text
max_connections = 4096
max_connections_per_ip = 4096
max_streams = 4096
max_subscriptions = 2048
max_subscribers_per_plugin = 64
http_idle_timeout_secs = 300
```

插件是无 UI 以外的普通服务：每个插件有 WebUI，payload 为
`exec tail -f /dev/null`，不带 `sleep`、不带子进程。

## 结果

```text
plugins              20
per_plugin_ws        50
total_ws             1000
ws_open              1000
handshake_seconds    0.86
seconds              60.1
daemonRssAvgMB       27.09
daemonRssMaxMB       27.09
pluginRssAvgMB       37.29
pluginRssMaxMB       37.29
totalRssAvgMB        64.37
daemonThreadsMax     10
daemonThreadsMin     10
daemonCpuPercent     2.91
pluginCpuPercent     0.00
```

## 解读

- 1000 条 WebSocket 全部保持打开，握手完成约 **0.86 秒**。
- daemon RSS 约 **27 MB**；20 个插件约 **37 MB**；总计约 **64 MB**。
- daemon 线程数全程稳定在 **10**，没有随 1000 条连接增长：
  - 说明 WebSocket 连接由 reactor/事件循环承载，不是每连接一条线程。
- 60 秒内 daemon CPU 约 **2.9%（单核）**，主要来自 1000 条 WS 的周期 ping/pong；
  插件进程 CPU 接近 0。
- 与 20 个普通插件基线（daemon ~4.2 MB、10 线程）相比，1000 条 WS 增加约
  **23 MB** daemon 内存，约 **23 KB/连接**（含连接状态、缓冲和订阅表）。
- low 档默认的 `max_connections_per_ip = 8`、`max_subscriptions = 4` 无法承载这个场景，
  所以压测必须显式提高这些上限；这不是默认配置下的可用容量。
