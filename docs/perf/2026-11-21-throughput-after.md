# 吞吐改造后的完整性能矩阵（2026-11-21）

本轮的五个改动（都已并入 main）：

| 提交 | 改动 | 作用 |
| --- | --- | --- |
| `45d36da` | SSE 事件唤醒 poll 循环 | 事件不再等 100 ms 轮询；SSE p50 131 → 20 ms |
| `6468aa0` | 单 ring + 订阅游标 | 实时扇出内存不再随订阅数增长，实时计数随预算放开 |
| `1475447` | `cpu_budget_percent` | 内核硬限（cgroup / Job Object）+ 准入闸门 |
| `74a5f2e` | 连接数由不变量反推 | 50 MiB 从 11 条连接变成 288/64 条（Linux/Windows） |
| `b35b5cb` | 阻断池随形状与连接数放大 | 线程 4/8/16，队列 min(连接数, 256) |

## 方法

```sh
python tools/perf/budget_scenario.py --binary <svcd> --budget <50mb|512mb|2gb> \
  --plugins 10 --per-plugin-concurrency <1|10|50|100> --duration 30 \
  --no-oversubscribe --bootstrap direct
```

- 每格 10 个插件、五面全开（invoke / SSE / WS / upload / download）、30 s。
- Win11 用 Python 插件；WSL2 用 bash shell 插件（用户要求，RSS 33 MB vs 182 MB）。
- 每插件并发 1 / 10 / 50 / 100 → 总 worker 10 / 100 / 500 / 1000。
- 客户端是 Python 线程（c100 即 1000 线程），高并发数字受客户端限制，见「归因」。

## 派生限制（启动时实际生效）

| 平台 | 预算 | 连接 | 流 | 订阅 | 阻断线程 | 阻断队列 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Windows | 50 MB | 64 | 64 | 64 | 4 | 64 |
| Windows | 512 MB | 340 | 340 | 340 | 8 | 256 |
| Windows | 2 GB | 709 | 709 | 709 | 16 | 256 |
| Linux | 50 MB | 288 | 288 | 288 | 4 | 256 |
| Linux | 512 MB | 399 | 399 | 399 | 8 | 256 |
| Linux | 2 GB | 786 | 786 | 786 | 16 | 256 |

Windows 的同预算连接数更低，因为不变量为「每连接一条线程」记账（tiny 的线程栈 128 KiB/条）。

## 归因

1. **c1 全部 100%**：三种预算、两个平台都满了。旧矩阵里 50 MB c1 是 82%（Win）/ 76%（WSL）。
2. **c10 是新的满血档**：Windows 512 MB 到 777.5 ops/s（CPU 890% = 8.9/16 核），WSL 到 327–350 ops/s。这一档在主线程池（阻塞池 8 线程 + 256 队列）以内。
3. **c50/c100 的失败是三类叠加**：
   - 50 MB Windows 只有 64 条连接（线程栈记账），100 个 worker 就超出；
   - 阻断池队列：c50/c100 的并发管理请求超过 256 槽（Windows 2 GB 的 c50 仍 100%，因为连接 709、队列 256 够用）；
   - 客户端与 fixture：WSL 的 bash 插件逐条处理 NDJSON，50 个并发调用排成队，把阻断池线程占满，于是 50 MB 的 c50 只有 21.8%；c100 的 1000 个 Python 线程本身也是瓶颈（Windows c100 只有 328–725% CPU，远未打满）。
4. **WSL 的 CPU 只到 2 核**：reactor 4 线程 + 16 线程池，c10 时 173–198%；同档 Windows 因为线程模型用掉 6–9 核。
5. **50 MB c10 的 cpu80 对照格**：可用率 80.7% vs 无预算 82.2%，daemon 只用了整机的 43%（695% / 16 核），所以 80% 的 CPU 预算没有生效——这是预期的（预算高于实际用量）。

阶段 1 固定每插件 1 并发、插件数 1→10；阶段 2 在 10 插件上抬并发。每格 12 s、五面全开，失败格复跑一次。

## 结论与下一步

- 预算不再是容量瓶颈：50 MB 从 11 条连接变成 288（Linux）/ 64（Windows）；满可用边界从 4 个并发 worker 变成 **120 个**（10 插件 × c12）。
- 目前的三个真实上限：**连接数**（50 MB Windows 64 条）、**阻断池队列**（256 槽）、**客户端**（1000 线程 / 串行 shell 插件）。
- 下一步排序：① Windows 端把线程栈换成 reactor（或按核数放宽 50 MB 的连接记账），② 客户端改 asyncio 才能测满 500/1000 并发，③ WSL fixture 换成能并行的插件（多进程或 asyncio），否则 c50 测的是插件而不是 daemon。
