# 20 插件 × 50 WebSocket：512 KiB raw binary 连续 60 秒

日期：2026-11-16  
平台：WSL2 Debian Linux x86_64  
构建：`cargo build --release`，默认 `MEM_LEVEL=high`  
连接：20 个 WebUI 插件，每个 50 条 WebSocket，共 **1000 条**  
数据：每条 WS 连续发送 **512 KiB binary frame**，服务端原样回显

## 实现范围

本次实现的是 **svcd WebSocket 层 raw binary 回显**：

- 允许 opcode `0x2` binary frame；
- 不做 JSON-RPC 解析；
- 原样返回 binary frame；
- 支持分片和 raw 大小上限。

**限制：** 还没有把 raw frame 透传到插件进程（protocol 3 raw framing 仍需实现）。
当前插件进程只负责连接和 UI token，raw 数据在 daemon WS 层回显。

## 与 512 KiB JSON echo 对比

| 路径 | 吞吐 | daemon RSS | 线程 | 错误 |
|---|---:|---:|---:|---:|
| JSON echo，20×50 连续 60s | 51.09 MB/s | 1.54 GB | 10 | 0 |
| raw binary echo，20×50 连续 60s | **184.04 MB/s** | **~696 MB** | 10 | 96 / 1000 连接 |

raw 路径明显减少了 JSON 解析/序列化开销，吞吐约 **3.6 倍**，daemon RSS 降低约 **一半**。

## 日志检查

`data.log` 共 62 行，前段稳定：

```text
t=01 done=0    open=1000 ...
t=02 ...
...
```

后段部分连接断开，最终：

```text
requests_completed = 22732
data_ok            = 22695
errors             = 96
ws_open            = 905
```

daemon stderr / `svcd.log` 没有 `panic`、`overflow`、`fatal`、`abort`、`too large`、`reset`。
但 **96 条连接在 184 MB/s 持续压测下断开**，说明当前 raw 回显路径还没有做完整的发送背压/慢客户端处理，不能直接作为生产稳定性结论。

## 结论

- raw binary 路径的吞吐和内存明显优于 JSON 路径。
- 1000 条 WS 线程仍为 **10**。
- 但 raw 插件透传尚未实现，且 1000 条 512 KiB 连续 raw 仍会有连接断开，需要：
  1. 实现 protocol 3 raw 到插件进程；
  2. 加入全局在途 raw bytes/requests 上限；
  3. 处理慢客户端发送队列，避免写缓冲无限增长/连接重置。
